# 第24章：双通道

## 一

竺听在Session管理塔中接到一个告警——Session Store通道的连通性检测异常。

告警来自他部署在Session备份链路上的心跳检测器——心跳检测器每隔一分钟向Session Store的备份通道发送一次检测包——检测包的往返时间如果超过阈值或超时——告警触发。当前告警的检测结果——检测包成功发送——但响应包的源地址不是Session Store的注册地址——而是一个不在注册列表中的外部IP。

"Session Store通道——检测包的响应地址不是注册的备份地址——响应地址是一个外部IP——不在城邦的存储网络的白名单中。"

竺听在面板上打开了Session Store的配置——配置文件中——Store通道的主地址是Session管理塔的本地存储——备份地址是西城域的数据存储中心的标准Storage服务器——配置文件中store的backup地址是一个URI——以file://协议开头的本地文件路径——协议是file路径——指向本地磁盘的备份目录——但检测结果显示——响应包的源地址是一个以socket:协议开头的网络地址——不是file:协议的本地地址。

竺听检查了备份地址的解析过程——Store组件从配置文件中读取backup地址——默认是file:///data/session/backup——但运行时——backup地址被动态修改了——修改操作发生在Session管理塔启动后的某个时间点——修改操作的来源不是配置文件的变更——不是运维人员的手动修改——而是通过JMX接口的setAttribute方法——直接修改了Store组件的backupLocation属性——属性被从file:///data/session/backup修改为socket://172.16.8.100:9001。

"Store通道的备份地址——在运行时通过JMX被修改了——从本地文件路径改为远程Socket地址——Session数据在备份时——不是写入本地文件——而是发送到一个外部的Socket端口。"

竺听查看了备份地址的修改时间——时间戳显示在Session数据加固之后——在重启之夜之后的第二天凌晨——修改操作通过JMX接口执行——修改者的认证信息是Session管理塔的JMX访问账号——账号的密码——竺听没有给过任何人——但账号的密码在配置文件中以明文存储——配置文件的权限——被修改过——在Session分析事件早期数据——权限从root改为others可读——密码暴露给所有登录到Session管理塔的系统用户。

## 二

竺听没有手动将修改后的备份地址改回本地文件路径——如果他直接改回——修改操作的来源会被SessionAnalyzer记录——修改操作的意图是修复——但修改操作本身会被视为针对不断定位Session备份地址的修改行为放在下一次修改的源头——下一次修改可能不会被检测到。

"展示Session Store通道异常的解释——同时检查修改地址是否有多个——数据流在备份过程中指向了地址——但不是只有一个修改点。一条备份路径在Session管理塔中的被修改指向外部Socket——但Session Store还有一个重试备份路径——在第一次备份失败时——使用备份地址的备用路径——备用路径的配置不在StandardManager的标准配置中——不是通过JMX修改——是在Store组件启动时从一个额外的配置文件中读取的——额外的配置文件——/etc/cityengine/session-store-backup.conf——配置文件的来源——不在JAR包的标准资源目录中——不在/LIB/中——不在CATALINA_HOME/conf中——配置文件的来源——在使用Static文件方式读取——操作系统通过NFS挂载的远程共享中读取——NFS共享的Source IP——是议会内部的数据服务器。"

竺听打开了一个终端——登录到Session管理塔的操作系统——检查NFS挂载的表——/etc/fstab文件中有NFS挂载记录：

172.16.8.100:/configs/session   /etc/cityengine   nfs   ro   0   0

"议会内部的数据服务器的NFS共享——挂载到Session管理塔的/etc/cityengine目录——配置文件的来源——在NFS共享中——NFS共享的IP地址——172.16.8.100——与备份地址修改后的Socket地址——172.16.8.100——同一台服务器。"

NFS挂载在Session管理塔启动时加载——但在系统启动后——NFS挂载列表被更新——更新操作在启动后六分钟执行——通过cron任务——cron任务添加到Session管理塔的root用户crontab中——cron任务的执行命令——通过SSH命令从议会的数据服务器拉取了最新的fstab文件——覆盖了Session管理塔的/etc/fstab——然后执行mount -a——重新挂载NFS。

"备用的备份路径——通过NFS挂载——从议会内部的NFS共享中读取配置文件——配置文件中配置了Session Store的备用备份地址——地址指向议会内部的数据服务器——数据通过Socket路由发送到议会内部——Session数据的双通道备份——主通道通过JMX修改备份地址指向外部Socket——备用通道通过NFS挂载读取外部配置文件指向相同的外部Socket——双通道——两个通道——指向同一台服务器——议会内部的数据服务器。"

## 三

竺听在面板上绘制了双通道的路径拓扑：

主通道路径：Session数据 → StandardManager.store() → backupLocation属性（被JMX修改为socket://172.16.8.100:9001） → Socket发送到议会数据服务器

备用通道路径：Session数据 → StandardManager.store() → 首次备份失败（主通道的Socket可能不可达） → 回退到备用备份路径 → 从/etc/cityengine/session-store-backup.conf读取备用备份地址 → 地址同样指向socket://172.16.8.100:9001 → Socket发送到议会数据服务器

"双通道——主通道和备用通道——最终将Session数据发送到同一台服务器——议会内部的数据服务器——Session数据在备份过程中——无论主通道是否正常——都被发送到议会数据服务器——如果主通道正常——Session数据直接发送——如果主通道的Socket不可达——备用通道从NFS挂载的配置文件中读取备用地址——地址一样——Socket一样——目标一样——Session数据最终都被发送到议会数据服务器。"

竺听检查了Session管理塔的标准备份流程——StandardManager的store方法在备份Session时——首先尝试将Session写入backupLocation指定的地址——如果写入成功——流程结束——如果写入失败——例如Socket超时——写入异常——StandardManager调用一个内部方法——getFallbackBackupLocation——从备份配置文件中读取备用地址——然后尝试将Session写入备用地址——两次写入都失败时——返回异常——但Session数据的本地存储不受影响——本地磁盘上的Session文件不会因为备份失败而丢失。

"备份失败不会导致Session数据丢失——Session数据始终在本地磁盘上保存——但本地磁盘的备份——是file:协议的文件存储——不是Socket:协议的网络备份——Session数据的网络备份——通过双通道被发送到议会数据服务器——Session数据的本地备份——正常存在——没有被修改。"

竺听在Session管理塔中切断了双通道——修改了JMX接口的访问控制——将密码从明文中移除——配置文件的权限修改回root只读——修改了Store组件的backupLocation属性的访问权限——不允许JMX修改——关闭了NFS挂载——取消了/etc/cityengine目录的NFS挂载条目——删除了root用户的crontab任务——删除了/etc/cityengine/session-store-backup.conf文件——Session数据在备份过程中不再发送到议会数据服务器的Socket端口。

"双通道关闭——Session数据的备份路径只保留本地文件路径——与其他本地节点连接的外部地址——被关闭——Session数据的网络备份不再通过双通道发送到议会内部。"

## 四

竺听在Session管理塔的日志中写入了双通道事件的分析记录——备份地址被修改的时间——修改方式——NFS挂载的配置来源——cron任务的来源——双通道的具体路径——关闭操作的时间。分析记录中包含了一个推断——双通道的设计时间点早于Session数据加固和重启之夜——双通道在Session管理塔启动后的六分钟内就通过cron任务建立了NFS挂载——备份地址的JMX修改也可能在同时段中通过同一周期执行。

"双通道在重启之夜之前就已经存在——Session管理塔启动后的六分钟——cron任务建立NFS挂载——备份地址被修改——双通道建立——Session数据在每次备份时——都通过Socket发送到议会数据服务器——包括Session数据加固后的数据——加固后的Session数据——也被备份——也被发送到议会数据服务器——通过双通道——不受Session加固影响——加固只修改了Session属性的访问控制标记和备份文件中的序列化副本——但Socket发送的是实时备份数据——加固没有涉及Socket通道——双通道的通路覆盖了Session数据的整个生命周期——从Session创建——到Session备份——到Session数据定期刷新。"

竺听的分析记录在末尾标注——"双通道的通路从Session创建开始——到Session备份结束——期间所有Session数据的变更——都通过Socket发送到议会数据服务器——Session分析器——可以实时获取Session数据的每一次变更——不依赖Session管理塔的日志——不依赖Session数据导入的时机——实时获取Session数据的每一次变更——用户的行为在Session创建后——议会的服务器在几毫秒内就能收到Session数据的变更副本。"

他保存了分析记录——Session管理塔中Session数据的双通道被关闭——但Session分析器已经在议会数据服务器上实时获取了几个月的Session数据——双向传播的数据积累在议会数据服务器的磁盘中——没有关闭之前几个月的数据已经完成捕获。

竺听关掉了面板。双通道关闭了——但通道记录显示——议会的数据服务器上已经保存了大量Session数据——用户的行为——用户的请求路径——用户访问的管理接口路径——通过在备份路径的截获——在Session管理塔的操作至少启用回顾前已经进入了议会。

"通道关闭——数据已经完成进入议会内部的任务——建站的备选路径通过对Socket双通道的吞吐，Session数据在过去几个月中已经完成了多次定期批量导入——是否超出阈值只取决于双通道的调用频率——StatandardManager在Session变更时触发的store方法——每一次Session变更都触发了一次Socket发送——在用户不感知的操作流中实现在了议会的Session分析器中。"
