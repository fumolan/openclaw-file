# 第26章：重新委派

## 一

温迟在类加载监管所中面对着两张修改方案。

一张是章副议长的备用体系方案——在Extension ClassLoader中注册了一个自定义URLStreamHandlerFactory——拦截对特定主机名的网络连接——将连接重定向到内部服务。具体来说——章的方案通过反射调用URL.setURLStreamHandlerFactory()——将默认的URLStreamHandlerFactory替换为一个自定义实现——自定义factory在收到ht、http等常见协议的handler创建请求时——先检查目标主机名是否在拦截列表中——如果在——返回一个转发到内部服务的handler——如果不在——返回null——由URL类中的fallback逻辑继续查找。

一张是温迟自己的修复方案——在全城范围内重置类加载体系——恢复双亲委派模型的完整性。

章副议长的备用方案已经被拆除——URLStreamHandlerFactory被温迟从Extension ClassLoader中移除——ClassShadowRegistry中的条目被清空——代理类加载器被停用。但移除后的Extension ClassLoader留下了一个问题：URLStreamHandlerFactory的修改操作破坏了工厂的单例模式——factory字段在第一次setURLStreamHandlerFactory()调用后不能再被修改——但章的备用方案在设置时替换了原来的factory——替换为自定义的factory——替换后的factory不从原始factory中委派——而是直接返回自定义的URLStreamHandler。原始factory的引用在替换时丢失了。

温迟在移除自定义factory时——需要恢复原始的factory引用——但原始factory已被覆盖——无法恢复。java.net.URL类的静态字段factory在第一次setURLStreamHandlerFactory()调用后被标记为final——后续的set调用会抛出Error。

"URLStreamHandlerFactory的单例模式被破坏后——无法回退。"温迟说。

## 二

温迟的修复方案是重新委派——在System ClassLoader的加载路径中增加一个新的URLStreamHandlerFactory——新的factory作为原始factory的代理——对URLStreamHandler的创建请求先在原始factory中查找——如果未找到——再在自定义的handler列表中查找。

重新委派的实现需要修改java.net.URL类的静态初始化块——在JVM启动时通过Java Agent注入字节码——修改URL的getURLStreamHandler()方法——在原有的handler查找逻辑之后——增加一个后备查找逻辑——从温迟维护的handler注册表中查找。

java.net.URL类的getURLStreamHandler(String protocol)方法内部包含一个多层查找逻辑：先检查缓存——handlerMap中是否已有该协议的handler——如果找到——直接返回。再检查factory——如果URLStreamHandlerFactory已被设置——通过factory.createURLStreamHandler(protocol)创建——如果返回不为null——存入缓存并返回。最后尝试通过系统属性加载——从java.protocol.handler.pkgs系统属性中读取包名——通过反射加载handler类——如果加载成功——存入缓存。

温迟的后备查找逻辑在factory.createURLStreamHandler()返回null之后——在系统属性加载逻辑之前执行。后备查找逻辑从温迟维护的ConcurrentHashMap<String, URLStreamHandler>中查找——如果找到——返回handler——如果未找到——继续执行系统属性加载逻辑。

"在factory和系统属性之间——插入一个后备查找层——不破坏原有的查找顺序——而是为factory的null返回提供了附加检查。"温迟在方案中写道。

## 三

温迟编写了RestoreAgent——一个Java Agent——在JVM启动时通过Instrumentation.addTransformer()注册一个ClassFileTransformer——在URL类被加载时修改其字节码。

RestoreAgent的字节码修改目标是getURLStreamHandler()方法。方法在原逻辑的返回语句前——插入一段新的字节码指令——检查返回的URLStreamHandler是否为null——如果为null——从温迟的agent注册表中查找指定协议的handler——如果找到——返回代理handler——如果未找到——返回null。

字节码的插入位置在方法的return指令之前——通过ASM框架定位到方法的第一个ARETURN指令——在ARETURN之前插入检查逻辑。检查逻辑的字节码指令序列为：

```
ALOAD 0                          // 加载this引用
GETFIELD java/net/URL.handlerMap  // 获取缓存map
ALOAD 1                          // 加载protocol参数
INVOKEVIRTUAL java/util/Map.get(Object) // 从缓存map中获取
DUP                              // 复制栈顶引用
IFNONNULL L_RETURN               // 如果找到handler，跳到返回
POP                              // 移除null
ALOAD 0                          // 加载this引用
GETFIELD java/net/URL.restoreHandler // 获取恢复handler
```

这个字节码序列很短——总共九条指令——对方法执行性能的影响在纳秒级别。温迟在部署前使用JMH基准测试进行了性能对比——带RestoreAgent的URL.openConnection()调用比不带Agent的调用多耗时约几十纳秒——对业务层的请求处理性能没有影响。

## 四

但RestoreAgent只能修复URLStreamHandler的查找逻辑——不能修复类加载器本身的问题。

章副议长的备用体系在类加载层面留下了一个更深层的隐患——双亲委派模型的信任链被破坏。TCCL的篡改让线程的上下文类加载器可以指向任意类加载器——代理类加载器可以从任意来源加载类——双亲委派的约束在TCCL层面被完全绕过。

温迟的修复方案是全城范围内恢复双亲委派模型的完整性——在每一个Context建筑的WebappClassLoader中植入检查逻辑——每次类加载请求在委派给父加载器之前——检查TCCL是否被篡改——如果被篡改——恢复为默认的WebappClassLoader。

具体实现：在WebappClassLoader.loadClass()方法的入口处——通过Thread.currentThread().getContextClassLoader()获取当前线程的TCCL——如果TCCL不是当前WebappClassLoader实例——且TCCL不在白名单中——通过Thread.currentThread().setContextClassLoader(this)将TCCL重置为当前WebappClassLoader。白名单包括所有标准类加载器——Bootstrap——Extension——System——Common——以及经过Engine议会签名的WebappClassLoader。

"每次类加载时检查TCCL——不是设置时检查——是使用时检查。因为攻击者可以在设置TCCL后不立即执行类加载——等到检查代码的执行间隔中再执行加载——使用时检查可以在加载前的最后一刻拦截。"温迟说。

## 五

温迟在监管所中部署了全城的类加载修复方案。

修复方案的部署分为三个阶段：第一阶段——在所有Context建筑中植入WebappClassLoader的TCCL检查逻辑——在第一周维护窗口内完成——影响的Context建筑数量为总体的四分之一。第二阶段——在所有Host域中部署RestoreAgent——修复URLStreamHandlerFactory的查找逻辑——在第二周维护窗口内完成。第三阶段——在所有Engine层级部署运行时类加载监控——定期扫描所有线程的TCCL和所有已加载类的签名——在第三周维护窗口内完成。

三阶段的部署在三周内完成。每次部署需要重启受影响的Context建筑——温迟在每周的维护窗口内执行部署——每次部署影响的Context建筑数量不超过总数的四分之一——保证城邦的整体服务不受影响。维护窗口是凌晨两点到五点——低流量时段——用户影响最小。

部署完成后——温迟打开了类加载监管所的监控面板。面板上显示——过去一周内——TCCL被非法篡改的事件数量为三件——全部被检查逻辑拦截并重置。新的代理类加载器无法再通过TCCL注册——旧的代理类加载器在运行中被逐渐回收——因为被篡改的类不再有新的加载请求——ClassLoaderGuard的签名校验会在旧类被重新加载时阻止加载。

类加载体系恢复了——但不是恢复到渗透前的状态——而是恢复到被修复后的状态。双亲委派模型的完整性在TCCL层面得到了增强——URLStreamHandler的查找逻辑增加了后备通道——类加载的运行时监控覆盖了所有活跃线程。

温迟在修复方案的最后一页写下了总结："类加载体系的修复不是回退——是重建。重建后的类加载体系增加了TCCL检查——URLStreamHandler后备查找——运行时签名验证——三道防线替代了原有的单一双亲委派防线。"

他关闭了监管所的白板。白板上的类加载拓扑图已经被更新——新的类加载体系在原有拓扑上叠加了三条虚线——TCCLGuard——ClassLoaderGuard——RestoreAgent——三道防线构成了新的类加载安全架构。

类加载的修复完成了——但类加载的战争没有结束。温迟知道——下一次的攻击不会走TCCL的旧路——它会选择新的攻击面——在温迟还没有设防的地方。但他的三道防线已经部署完成——新的攻击会在防线外被发现——在造成损害之前被拦截。

温迟关上了监管所的门。类加载监管所的灯光在深夜中持续亮着——监控面板上的数字在规律地跳动——没有异常。
温迟在全城部署完成后的第二天检查了所有Host区的类加载日志。日志显示TCCL的违规调用频次归零——没有模块再通过线程上下文绕过父加载器注入实现类。SPI模块的显式委派配置正常运行，驱动加载路径可控、可审计、可追溯。他在自己的工作总结中记录了一行确认语句："双亲委派模型已还原。违规注入路径已阻断。SPI模块切换为显式加载——加载日志可追溯。全城类加载体系状态——正常。"语句结束。没有多余字符。他知道真正重要的不是把这行字写在纸上，而是这行字描述的状态已在所有节点的类加载架构层内物理落实。

温迟关上监管所的门之前回头看了一眼监控面板。数据还在跳动——但没有异常。他想起三周前第一次发现TCCL被篡改时的情形——那时面板上的异常标记像警报灯一样闪烁——每个异常标记代表一个被代理类加载器加载的类——每个被篡改的类都可能正在执行恶意代码。三周后——面板上的异常标记全部消失——类加载生态在修复后重新进入稳定状态。

他在监管所门口站了几秒——然后关上了门。类加载的修复不是终点——但他知道至少在这一层——城邦的防线已经加固了。
这不是结束——但至少——温迟可以暂时关上灯了。
