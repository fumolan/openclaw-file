# 第15章：假醒

## 一

步桐在西五车间的调度面板上发现了一个奇怪的现象——一个被Guarded Suspension模式保护的队列——线程在等待条件时——突然被唤醒——但条件并不满足。

"虚假唤醒。"步桐说。

西五车间的代码——消费者线程从队列中取数据。队列为空时——消费者进入等待——等待分配器通知队列中有新数据。等待代码写的是——if (queue.isEmpty()) { lock.wait(); }。

但实际运行中——消费者线程被唤醒后——队列仍然为空——消费者没有检查条件——直接调用queue.poll()——返回null——消费者对null数据进行非空操作导致执行出错。

"A线程wait()后被唤醒——但队列没有数据——A假设队列有数据——直接取——取到null——null处理逻辑不在代码中——线程抛出NullPointerException。"

步桐调出JVM规范——Thread.interrupt()的语义——notify()和notifyAll()唤醒等待线程后——被唤醒的线程不会立即执行——而是竞争锁——获取锁后从wait()返回。但在某些操作系统上——线程可能在没有任何notify()调用的情况下被唤醒——这就是虚假唤醒。

"Guarded Suspension模式——线程在某个条件不满足时等待——条件满足时被唤醒——继续执行。"步桐在面板上写。"标准实现——wait()必须在循环中调用——而不是if判断——while (!condition) { lock.wait(); }——而不是if (!condition) { lock.wait(); }。"

步桐查阅了JVM规范——Object.wait()的文档明确写道："线程可能被虚假唤醒——即使没有调用notify()或notifyAll()——break或interrupt——所以在wait()返回后——应该重新检查等待条件。"

"不是bug——是特性。"步桐说。"JVM允许虚假唤醒——操作系统也允许。任何等待条件的实现——都必须用while循环——而不是if。"

## 二

步桐在西五车间检查了所有使用wait/notify模式的代码——一共十七个地方——其中十四个用了while循环——三个用了if。

"十四个合格——三个不合格。"

步桐改写了三个if——全部改为while。同时检查了notify/notifyAll的使用——全都没问题——所有使用wait()的线程都采用lock对象共享——notifyAll()统一唤醒。

她打开一个典型的Guarded Suspension代码剖析——生产者-消费者模式。

while (queue.isFull()) { lock.wait(); }——消费者在队列满时等待——条件不满足——继续等待。当消费者消费数据——队列不满——消费者调用lock.notifyAll()——唤醒所有在lock上等待的生产者——生产者从wait()返回——重新检查条件——if(!queue.isFull())——条件满足——生产者继续执行——添加数据。

"条件通知模式——notifyAll()通知所有等待线程——每个线程独立检查自己的条件。不是'通知一个线程去执行'——而是'通知所有线程检查条件'。"

步桐继续在规范上写："Guarded Suspension——条件检查必须用while——不能用if。notifyAll()——比notify()更安全——因为notify()唤醒的线程可能是等待其他条件的线程——条件不满足——再次等待——浪费一次唤醒。"

## 三

步桐在西五车间检查虚假唤醒的场景时——发现了另一个相关的问题：InterruptedException的处理。

步桐观察了一下西五车间被虚假唤醒的消费者被标记为InterruptedException的异常日志——在任务处显示的是一个WRONG DATA的异常——消费者从队列中取出的数据是null——但在改为了while循环后——即使被虚假唤醒——线程也会重新检查条件——队列为空——继续等待——不会处理null数据。

但InterruptedException的捕获位置也在wait()调用处——如果线程在wait()期间被中断——wait()抛出InterruptedException——JVM会同时清除线程的中断标志——中断标志位变为false。

"InterruptedException的捕获——被捕获后——中断标志被清除。"步桐说。"如果线程的业务逻辑依赖中断标志——需要重新设置中断标志位。"

步桐在Guarded Suspension的规范中追加了InterruptedException的处理规则："如果线程在wait()期间被中断——捕获InterruptedException后——必须重新设置中断标志——Thread.currentThread().interrupt()——或者throw异常——不能吞掉中断信号。"

"吞掉中断信号——上层代码无法知道线程被中断——线程行为异常。"

## 四

步桐在西五车间对Guarded Suspension模式做了全面的梳理——从生产者到消费者——从条件检查到中断处理——从虚假唤醒到通知策略。

她在车间协作面板上贴出了Guarded Suspension的标准模板：

"锁对象——lock——final Object——所有生产者和消费者共享。条件——queue.isEmpty()或queue.isFull()——在while循环中检查。等待——while (condition) { lock.wait(timeout); }——加上超时——防止永久等待。通知——lock.notifyAll()——在条件变化后调用——不调用notify()。中断——捕获InterruptedException——重新设置中断标志——Thread.currentThread().interrupt()——或者throw。"

步桐站在面板前——把所有使用Guarded Suspension模式的车间——在分派系统上做了一个统一标注。标注的内容——检查是否使用while——检查是否有中断处理的逻辑——检查notifyAll()的使用。

"虚假唤醒是操作系统的特性——不是bug——但如果不处理——就是bug。"

步桐巡察了一下午——十七个使用wait/notify的代码点——十四个已正确使用while——三个改成了while——十三个使用notifyAll()——四个使用notify()——四个notify()也改成了notifyAll()——在两个notify()的case中——只有一个预期被唤醒的线程——notify()和notifyAll()的效果一样——但为了安全——全改。

## 五

步桐完成了西五车间的虚假唤醒修复。

她在工作日志上写下总结："Guarded Suspension——线程在条件不满足时等待——条件满足时被唤醒。关键点——wait()必须在while循环中调用——防止虚假唤醒。notifyAll()比notify()更安全——防止唤醒错误的条件等待线程。中断信号不能吞掉——必须重新设置中断标志——否则上层代码不知道线程被中断。"

"Guarded Suspension不是高深的技术——是基本的并发模式——但越是基础——越容易被忽略。"

步桐走出西五车间——夜幕将下了。车间内的线程在调整后的Guarded Suspension模式保护下——队列为空时——消费者在while循环中wait()——队列有数据时——被notifyAll()唤醒——重新检查条件——有数据——取数据——处理——完成。

她在门口停顿了一下——听到车间里线程在等待和唤醒之间循环工作的低音——稳定的节奏——没有中断——没有空指针——没有虚假唤醒的干扰。

步桐相信——在每个消息等待的时刻——同步层的工作就是要保证——等待的人等到的是正确的事。
