# 第14章：两阶段终止

## 一

申琥在南一车间的线程状态监控面板上发现了一个异常的线程。

面板上的线程列表——三十二个活跃线程——三十一个在RUNNABLE和TIMED_WAITING之间正常切换——一个线程——线程T-512——状态始终是TIMED_WAITING。面板显示——T-512从四个小时前进入TIMED_WAITING状态——之后再也没有变化。

"四个小时——同一个状态——没有切换。"申琥说。

他调出T-512的调用栈——T-512在一个阻塞队列的take()方法上——调用了poll(30, TimeUnit.SECONDS)——在超时时间为30秒的线程等待中。poll(timeout)在指定时间内等待队列中有数据——如果队列为空——线程进入TIMED_WAITING——等待超时或队列中有数据——醒来——检查条件——如果队列仍然为空——再次调用poll(timeout)——进入下一轮TIMED_WAITING。

"不是永久阻塞——超时后线程会醒来——但醒来后——又进入下一轮等待。"

申琥查看了T-512的堆栈日志——确实——线程在每三十秒超时一次——醒来——发现队列仍然为空——再次调用poll(timeout)——再次进入TIMED_WAITING。线程一直在周期性地"微活"再进入等待——但四个小时内——没有任何数据被消费。

"线程活着——但没有干活。"申琥说。

他检查了T-512的中断状态——interrupt标志——未设置。没有其他线程发送中断给T-512。队列持续为空——不是因为数据被其他线程消费了——而是数据根本不来。

申琥向生产系统发送了一个中断请求——Thread.interrupt()。他想看看T-512是否会响应中断——退出等待——执行清理——然后结束。

interrupt()发送后——监控面板上T-512的中断响应标志变为true。但T-512拒绝响应中断——线程在poll()上继续等待。堆栈跟踪显示——poll(timeout)在收到中断请求后没有抛出InterruptedException——因为poll(timeout)的调用者在被中断后会继续等待下一轮——它没有检查中断状态。

"中断信号被忽略了。"申琥说。

## 二

申琥查看了T-512的完整代码——一个消费者线程——从阻塞队列中取数据——处理——逻辑在一个无限while循环中。

while (true) { String data = queue.poll(30, TimeUnit.SECONDS); if (data != null) { process(data); } }

代码逻辑——循环内反复poll——队列有数据就处理——队列没数据等三十秒——等完继续poll——永不退出。interrupt()发送后——poll(timeout)内部在收到中断后重新设置线程的中断标志——但while循环的下一次迭代——不检查中断标志——继续poll——中断效果只是短暂地中断了当前的poll等待——没有改变线程的生命周期。

"需要两阶段终止。"申琥说。

"第一阶段——线程收到中断请求——设置中断标志——表示"主人希望我停止"。第二阶段——线程在合适的时间检查中断标志——如果被中断——执行清理操作——退出循环——线程终止。"

"两阶段终止的核心思想——'请求终止'和'响应终止'分离。请求终止——调用interrupt()——只是一个信号。响应终止——线程在某个时机检查中断标志——如果信号来了——优雅地退出——释放资源——执行清理——不是被人一把拉死。"

## 三

申琥改写了T-512的循环逻辑。

第一阶段——外部调用T-512.interrupt()——设置线程的中断标志。第二阶段——线程在循环的每次迭代开始时检查Thread.currentThread().isInterrupted()——如果为true——退出循环——执行清理——线程终止。

改造后的代码：

while (!Thread.currentThread().isInterrupted()) { try { String data = queue.poll(30, TimeUnit.SECONDS); if (data != null) { process(data); } } catch (InterruptedException e) { Thread.currentThread().interrupt(); break; } }

几个关键点——第一——isInterrupted()检查线程的中断标志——返回true表示线程被要求终止——返回false继续正常循环。第二——InterruptedException捕获——poll(timeout)在等待期间如果线程被中断——抛出InterruptedException——捕获异常后重新设置中断标志——因为JVM在抛出InterruptedException后会清除中断标志——需要重新设置——然后break退出循环。第三——线程退出循环后——执行清理——关闭可能已使用的资源——包括关闭相关的网络连接、I/O流——然后线程自然终止。

"这样——interrupt()后——线程不会立即停止——不会抛出InterruptedException——线程在检查中断标志时发现被中断——然后优雅退出。"

申琥解释——两阶段终止的完整流程："第一个阶段——调用者线程向目标线程发送终止信号——interrupt()——设置中断标志——不做其他操作。第二个阶段——目标线程在自己的循环逻辑中——在合适的时间点检查中断信号——isInterrupted()捕获中断——退出循环——也可以catch InterruptedException——进一步响应——退出循环。两阶段——请求和响应——分离——目标线程掌握自己何时退出的主导权——不是被强制终止。"

## 四

申琥部署了新的T-512代码——在两阶段终止逻辑中——加入了一个额外的清理步骤——如果线程在被中断时队列中还有数据——把剩余数据写入持久存储——避免数据丢失。

"线程终止时——队列中可能还有待处理的数据。"申琥说。"两阶段终止的一个优势——线程在退出前——可以执行清理操作——保存未完成的工作——关闭打开的资源——写最后的日志。"

申琥在清理阶段加入了一个dataDrain操作——将队列中剩余的所有数据写入一个临时存储文件——供另一个线程后续处理。

"线程优雅退出——不留下不完整的数据。"申琥说。

他重新启动了T-512。监控面板上——T-512的状态变为RUNNABLE——开始轮询队列——队列为空——TIMED_WAITING——三十秒后醒来——队列仍然为空——检查中断标志——false——再次poll——TIMED_WAITING。

申琥发送了一个interrupt()信号。T-512的监控面板上——isInterrupted标志变为true——T-512在下一轮循环开始时——检查中断标志——发现true——break退出循环——执行dataDrain——队列中剩余数据被写入文件——线程终止——状态变为TERMINATED。

"终止完成。干净——安全——没有数据丢失。"

## 五

申琥在南一车间解决了T-512的问题。但问题不是个案。

他在线程面板上搜索——所有使用无限循环的线程——加上poll或take的等待——加上sleep——都可能面临中断不响应的风险。

面板返回了一个列表——十三个线程——在循环中使用sleep()或poll()——但没有两阶段终止逻辑。interrupt()后——这些线程会忽略中断信号——继续等待——继续轮询——线程永远不会终止。

申琥在这个列表中的每个线程上都应用了两阶段终止模式——在每个无限循环中——加入isInterrupted()检查——在catch InterruptedException中——重新设置中断标志——优雅退出逻辑。

他在规范面板上写下："所有可中断的线程——必须实现两阶段终止模式。interrupt()只是请求信号——不是终止命令。线程必须在自己的循环逻辑中检查中断标志——在合适的时间退出。不要在catch InterruptedException后吞掉中断——必须重新设置中断标志——或者throw——否则其他代码无法知道线程被中断。"

"两阶段终止——不是Java API——是一种模式。"申琥在规范的最后写。"Thread.interrupt()的语义是'请停止'——不是'停'。响应权在线程自己。"

南一车间的监控面板上——T-512已经终止——状态是TERMINATED。其他十三个线程——修改后——每个都能够在收到interrupt()后优雅退出。

申琥走出南一车间——他知道——两阶段终止的背后——是对线程生命周期完整的尊重——不强杀——不强制——只请求——让线程自己决定在什么时候停止。这是并行城中线程员工作为独立执行单元的最后尊严。
