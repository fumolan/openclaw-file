# 第27章：先来后到

## 一

卫濡在西七路账务车间发现了一个熟悉的东西——死锁——两个线程——同时持有两个锁——等待对方释放锁——互相等待——谁都无法前进。

"又死锁了。"卫濡说。西七路车间——转账业务——线程A从张三的账户向李四的账户转账——先锁张三的账户——再锁李四的账户——执行转账——释放锁。线程B从李四的账户向张三的账户转账——先锁李四的账户——再锁张三的账户——执行转账——释放锁。

A锁张三——B锁李四——A等待李四——B等待张三——环形等待——死锁。

"加锁顺序不一致——两个线程——一个正向——一个反向——锁的顺序冲突——死锁。"

卫濡查看了西七路账务车间的代码——转账操作——参数是两个账户ID——代码逻辑是——lock(accountFrom)——lock(accountTo)——transfer(from, to, amount)——unlock(to)——unlock(from)。但问题是——这两个参数——谁先谁后——没有规定——线程A调用transfer("张三", "李四", 100)——先锁张三后锁李四——线程B调用transfer("李四", "张三", 50)——先锁李四后锁张三——顺序不一致——死锁。

"统一加锁顺序——把参数排序——不管传入的顺序是什么——始终按照统一规则加锁——比如按账户ID的哈希值——小的先锁——大的后锁——就不会出现等待冲突——不会死锁。"

## 二

卫濡设计了统一加锁顺序的方案——所有涉及多个锁的代码——先对锁对象排序——按照账户ID的hashCode排序——hashCode小的先锁——hashCode大的后锁。

卫濡修改了西七路车间的转账代码——private final Object lock1 = account1.getId().hashCode() < account2.getId().hashCode() ? account1 : account2; private final Object lock2 = account1.getId().hashCode() < account2.getId().hashCode() ? account2 : account1;——不管传入的账户顺序是什么——都先锁hashCode小的——再锁hashCode大的。

"加锁顺序统一——两个线程都先锁张三——再锁李四——不存在环——死锁解除。"

改造后——线程A调transfer("张三", "李四", 100)——张三的hashCode小于李四——先锁张三——再锁李四——转账。线程B调transfer("李四", "张三", 50)——同样——张三的hashCode小于李四——先锁张三——再锁李四——还是先锁张三再锁李四——两个线程的锁顺序一致——不存在轮——就绪——可顺序——先锁张三的线程获得张三锁——后锁张三的线程等待张三锁——但不会出现A锁张三、B锁李四——环形等待——无死锁。

"加锁顺序——一个简单的排序规则——消除死锁的环。不是所有情况都适合——但适合多个锁有确定可排序的场景——账户ID——订单ID——无论什么ID——有一个统一的可排序键——就能消除因顺序导致的环形等待。"

卫濡补充——如果hashCode冲突——两个不同的账户ID可能有相同的hashCode——这时需要额外的机制——比如使用System.identityHashCode()——如果还冲突——定义一个额外的锁——tieLock——在hashCode相同时——先获取tieLock——再获取锁——tieLock保证——hashCode相同的锁——只有一个线程能同时持有。

## 三

统一加锁顺序的方案上线后——西七路车间的死锁的确消失了——但卫濡又发现了一个新问题——两个锁的跨度——不同线程持有两个锁的持续时间不同——线程A持有张三的锁——等待李四的锁——持有时间长——大量转账请求等待张三的锁——排队——性能下降。

"统一加锁顺序消除了死锁——但不能消除锁竞争——A持有张三的锁——等待李四的锁——其他需要张三锁的线程——排队——串行化。"

卫濡检查了转账逻辑——锁的范围太宽——持有锁的同时执行了整个转账流程——包括数据库操作——包括更新其他数据表——包括发送通知——整个过程在持有两个账户锁的情况下完成——锁范围太大——等待时间太长——锁竞争加剧。

"加锁的范围——越小越好。只保护必须保护的操作——不保护非必要操作。"

卫濡重构了转账代码——把大的锁范围拆细——先持有一个锁——查账户余额和基本信息——数据库操作——但不需要锁保护——因为数据库自身有事务。再获取两个账户锁——只保护转账金额的更新——扣除from账户——增加to账户——update操作——完成后释放锁——再发送通知——但通知不在锁内——不持有锁执行不必要的操作。

"锁的范围——只保护共享资源的操作——其他操作在锁外执行——锁持有时间减少——锁竞争减少——性能提升——死锁风险降低。"

卫濡调整后——锁的持有时间从平均35毫秒降到3毫秒——减少了90%的锁持有时间——但加锁顺序规则不变——先hashCode小的——再大的——死锁可能性为零——因为锁的范围小了——但锁顺序不变——不存在环。

## 四

卫濡把视线扩大到西七路车间所有涉及多锁的代码——不只是转账——还包括订单处理——库存更新——权限验证——每个涉及多个锁的模块。逐一检查加锁顺序是否统一。

结果——问题很多。不同模块——不同团队——不同的加锁顺序——各加各的——各锁各的——规则不统一——规则不一致——锁顺序冲突——跨模块交互时——不同的顺序——死锁。

"系统的死锁——不仅仅是单个模块内两个锁的顺序不一致——而是多个模块间——加锁顺序的不一致——跨模块交互——死锁风险更大。"

卫濡设计了一套全系统的加锁顺序规范——所有锁对象——按全局统一规则排序——按照对象类型——类型内的对象按ID的hashCode排序——类型间按类型名称的字母顺序排序——全部锁定了。

"一个全局的加锁顺序——系统内所有锁——都有固定的排序——不管哪个模块——不管什么场景——加锁时必须按照这个顺序——不遵守——就是bug——code review不通过——死锁风险不可控。"

卫濡和程锁商量——把这个规则纳入互斥层的编码规范——所有涉及多个锁的代码——必须按照全局加锁顺序——违反规则——合并请求时自动CI检测——锁的顺序规则在CI中检查——PR中——静态分析工具——扫描lock()的调用顺序——与全局锁顺序表对比——不一致——标记——通知开发者。

"不是在出事后修——而是开发中就不允许锁顺序不一致的存在——从一开始——死锁风险就被工具屏蔽。"

## 五

卫濡站在西七路车间门口——死锁日志已经连续一个月为零——统一加锁顺序——加上锁范围缩小——加上CI检测——死锁被系统性消灭——不是靠碰运气——不是靠代码review——是靠规则——工具——流程——三位一体。

"加锁顺序——不是解决所有死锁——是解决锁顺序冲突导致的死锁。还有锁嵌套导致的死锁——锁与锁之间的条件依赖导致的死锁——但统一加锁顺序——是最简单、最有效、最易执行的死锁预防策略——推广性最强——效果最确定——没有之一。"

卫濡在规范面板上写下加锁顺序规范——"第一——所有涉及多个锁的代码——必须按照全局统一锁顺序获取锁——无论参数顺序如何。第二——如果锁对象有可比较的ID——按ID的hashCode排序——小的先锁——大的后锁。第三——如果ID相同——使用tieLock——额外定义与系统不相关的锁——只在这种hashCode冲突场景使用。第四——锁范围最小化——只保护必要操作——非共享操作不在锁内。第五——CI中自动检测加锁顺序违反——违反不通过——自动拒绝合并。"

"加锁顺序——不复杂——但需要全系统统一执行——一个模块的例外——就是整个防线的缺口。死锁不可怕——可怕的是——死锁本可以被预防——但没有预防。"

卫濡走出西七路车间——车间里的转账操作——锁顺序统一——锁范围精确——锁持有时间短——没有死锁——一个月——没有死锁日志——记录——转账完成。加锁顺序——为西七路车间——也为整个并行之城——打下了一个稳固的秩序基础。
