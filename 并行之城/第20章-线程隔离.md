# 第20章：线程隔离

## 一

阮钴在南五车间发现了一个问题——线程复用后读到了脏数据。

南五车间的数据处理器——使用线程池处理数据。每个线程在处理数据时——创建一个ThreadLocal变量——存储当前数据的上下文信息。数据处理完成后——线程返回线程池——等待下一个任务。

问题在于——线程返回线程池后——ThreadLocal变量没有被清理。下一个任务复用同一个线程时——ThreadLocal变量仍然保留着上一个任务的数据——当前任务读取到上一个任务的脏数据。

"ThreadLocal没有被清理。"阮钴说。

他调出了ThreadLocal的使用代码——每个任务开始时——threadLocal.set(context)。任务处理过程中——threadLocal.get()获取上下文。任务结束时——代码没有调用threadLocal.remove()。线程返回线程池——ThreadLocal变量仍然存在。下一个任务开始时——threadLocal.set(context)覆盖上一个任务的值——但如果新任务没有调用set()——直接调用get()——获取到的是上一个任务的值。

"ThreadLocal的生命周期——与线程的生命周期相同。"阮钴在面板上解释。"线程不销毁——ThreadLocal变量不销毁。线程池中的线程是复用的——线程不销毁——ThreadLocal变量不销毁——除非显式调用remove()。"

阮钴举了一个例子——线程T1处理任务A——ThreadLocal存储了任务A的用户ID为"用户001"。任务A完成后——线程T1返回线程池——ThreadLocal中的用户ID仍然是"用户001"。线程T1被分配给任务B——任务B没有调用threadLocal.set()——直接调用threadLocal.get()——获取到的是"用户001"——但任务B的用户应该是"用户002"——脏数据。

"ThreadLocal泄漏——不仅导致脏数据——还导致内存泄漏。"阮钴说。"ThreadLocal变量存储在线程的ThreadLocalMap中——ThreadLocalMap的key是ThreadLocal对象的弱引用——value是强引用。如果ThreadLocal对象被回收——key变为null——但value仍然存在——无法被垃圾回收——内存泄漏。"

## 二

阮钴在南五车间搜索了所有ThreadLocal的使用——一共十二处。其中八处在任务结束时调用了remove()——四处没有调用。

"四处漏洞。"阮钴说。

他逐一修复——在任务结束的finally块中增加threadLocal.remove()。finally块保证即使任务抛出异常——remove()也会被执行。

修复代码模板：

try {
    threadLocal.set(context);
    // 处理任务
} finally {
    threadLocal.remove();
}

阮钴强调——remove()必须在finally块中调用——不能在try块的末尾调用——如果任务抛出异常——remove()不会被执行——ThreadLocal泄漏。

## 三

阮钴进一步分析ThreadLocal的原理——每个线程有一个ThreadLocalMap——ThreadLocalMap存储了该线程的所有ThreadLocal变量。ThreadLocalMap的key是ThreadLocal对象的引用——弱引用。value是ThreadLocal.set()传入的值——强引用。

"弱引用key——在ThreadLocal对象没有外部强引用时——可以被垃圾回收。"阮钴说。"key被回收后——变为null——但value仍然是强引用——无法被回收。"

"ThreadLocalMap的value泄漏——在线程长期存活的场景下——例如线程池——线程不销毁——ThreadLocalMap不销毁——泄漏的value不销毁——内存持续增长。"

阮钴在南五车间的JVM监控中看到了内存增长——线程池有二十个线程——每个线程的ThreadLocalMap中有四个泄漏的value——每个value大约1KB——总共80KB。看起来不大——但长时间运行后——泄漏的value累积——内存增长到几百MB。

"内存泄漏——缓慢但持续。"阮钴说。"必须调用remove()清除value。"

## 四

阮钴在南五车间制定了ThreadLocal的使用规范。

"ThreadLocal的正确使用——每次使用前set()——每次使用后remove()。"阮钴在规范中写。"set()和remove()必须成对出现——在finally块中调用remove()——保证异常情况下也能清除。"

"ThreadLocal的适用场景——线程隔离——每个线程需要独立的变量副本——线程之间不共享。例如——用户上下文——每个请求的用户信息存储在ThreadLocal中——线程之间的用户信息隔离。例如——日期格式化——SimpleDateFormat不是线程安全的——每个线程使用独立的SimpleDateFormat实例——存储在ThreadLocal中。"

"ThreadLocal的不适用场景——线程之间需要共享数据——使用共享变量——不是ThreadLocal。线程池场景——必须调用remove()——否则泄漏。"

阮钴补充了一个最佳实践——使用Java 8的ThreadLocal.withInitial()——提供初始值——避免null值。

ThreadLocal<String> userId = ThreadLocal.withInitial(() -> "默认用户");

"withInitial()——在get()时如果没有set()——返回初始值——避免null。"

## 五

阮钴完成了南五车间的ThreadLocal泄漏修复——四处漏洞全部修复——内存增长停止——脏数据问题消失。

他在工作日志上写下ThreadLocal的使用总结：

"ThreadLocal——线程隔离——每个线程独立的变量副本。生命周期与线程相同——线程不销毁——ThreadLocal不销毁。线程池场景——线程复用——ThreadLocal泄漏——必须调用remove()。"

"remove()必须在finally块中调用——保证异常情况下也能清除。set()和remove()必须成对出现——不成对就泄漏。"

"ThreadLocal的原理——ThreadLocalMap存储在线程中——key是ThreadLocal对象的弱引用——value是强引用。key被回收后——value仍然是强引用——内存泄漏。"

"ThreadLocal的适用场景——线程隔离——用户上下文——日期格式化——随机数生成器。不适用场景——线程之间共享数据。"

阮钴走出南五车间——ThreadLocal的名字听起来像是线程本地——但实际上是线程隔离——隔离数据——隔离问题。隔离的好处——线程之间不干扰。隔离的风险——忘记清理——脏数据——内存泄漏。理解ThreadLocal的生命周期——正确使用——才能真正隔离问题而不是制造问题。
