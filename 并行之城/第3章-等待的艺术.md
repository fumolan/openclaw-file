# 第3章：等待的艺术

## 一

步桐接到北五车间的紧急呼叫时，车间里已经乱成一锅粥。

装配工A的工位前堆满了半成品——他已经完成了三道工序，等着装配工B把零件送到他的进料口。但装配工B的工位是空的。座椅上没有人。显示器上没有操作。

"B呢？"步桐问。

"两个小时前就开始等了。"车间主管说，"A在等他送零件。B就一直坐着——没动。"

步桐走到B的工位前看了看面板。面板上显示B的线程状态——WAITING。不是RUNNABLE，不是BLOCKED，不是TIMED_WAITING——纯粹彻底的WAITING。JVM线程状态中的一种——线程释放了锁，进入了锁对象的等待集(WaitSet)，在等待另一个线程在同一个锁对象上调用notify()或notifyAll()。唤醒之前，线程不消耗CPU，不参与调度。但不是TIMED_WAITING——没有设置超时参数，所以这次等待可能是永久性的。

"他怎么进去的？"

主管调出了B的操作日志。日志显示：B在两个小时前检查了零件缓冲区——当时缓冲区为空。B调用了wait()——释放了它持有的锁，进入了等待集，等待另一个线程通知它缓冲区有新零件。进入等待集的瞬间，B的锁被释放——其他线程可以获取这个锁。

但问题在于——A在等B。B在等A通知它"可以送零件了"。A不知道B在等通知。B不知道A在等他去拿零件。

"A没调notify()。"步桐说。

"A不知道要调。"主管说，"A的工序里没有notify()这一步——"

"A不知道。但B不知道A不知道。于是两个线程各等各的——一个在等待通知，一个在等待被通知的人来通知他。B死锁在了自己的协作逻辑里。"

## 二

步桐把A和B的调用栈同时拉出来看了。

A的调用栈：executeStep4() → waitForMaterial() → 在这个方法里循环检查缓冲区标志位，没有调用wait()，用的是Thread.sleep(1000)轮询。每秒检查一次——CPU空转轻度浪费，但至少不会永远卡住。

B的调用栈：executeTransport() → checkBuffer() → 发现缓冲区为空 → wait() → 等待集。锁对象释放了。没有设置超时。没有设置唤醒条件之外的其他退出机制。B的线程在WaitSet中——不消耗CPU——但永远不会被唤醒。

"A用轮询。"步桐说，"B用无超时的wait()。两种方式都不对，但B的方式更致命——有CPU空转比彻底卡死好。"

"为什么？"主管问。

"轮询至少可以恢复。"步桐说，"空转虽然浪费资源，但线程还在跑——一旦缓冲区有数据，A能在最多一秒内检测到。但B进入到wait()之后——除了等着被notify()，没有任何办法退出。没有超时，没有中断，没有其他退出路径。一旦notify()永远不会发生，B就永远留在等待集里。"

主管说："那如果A后来设置了标志位——"

"A不会调用notify()。A的代码里没有那个步骤。就算A在某一时刻发现ready了——A只是修改了标志位，然后继续做自己的事。B不知道。B还在等那个永远不会到来的notify()。"

## 三

步桐在车间里查看了A和B的完整代码。

A的代码——简单粗暴。while (!materialReady) { Thread.sleep(1000); }。materialReady是一个volatile boolean变量。A不使用锁，不使用wait/notify——只是每隔一秒检查一次标志。A的逻辑：我完成了前三道工序，我把状态设为等待材料到达，然后循环检查。

B的代码——B在检查缓冲区为空后，调用了wait()。没有设置超时。公共锁对象——车间初始化时的一个Object实例。B在锁对象上wait()之前，获取了锁对象的monitor——synchronized(lock)内的wait()调用。之后释放锁，进入等待集。

A的代码中从来没有获取过lock对象——A不使用锁，不使用wait/notify，不知道lock的存在。A和B之间没有任何共享的同步对象。B在等A通知他——但A没有lock的引用，无法调用notify()。如果强制A调用lock.notify()——JVM会抛出IllegalMonitorStateException——因为A没有获取lock的monitor。

主管问："把A改成也用wait/notify不就行了？"

"不行。"步桐说，"A在多个地方都会等待材料到达。其中有一个场景——材料到达的信号是通过中断处理器设置的。中断处理器不是线程——它不持有任何锁。如果A在锁对象上wait()，中断处理器在设置materialReady标志后，没有机会调用notify()——它不在synchronized块内。"

"那怎么办？"

"两个选择。"步桐说，"一——保持A轮询但要降频率。二——在A和B之间加一个共享信号层。"

步桐选了方案二。

## 四

步桐在A和B之间加了一个中间层。一个AtomicBoolean——同时被A和B引用。

当B在LOCK上wait()之前，先检查这个原子变量——如果为true，说明A已完成前三道工序，B可以直接送材料，不需要等。

当A完成前三道工序后，设置这个原子变量为true。A设置原子变量的代码被放在一个synchronized(LOCK)块里，在设置后调用LOCK.notifyAll()。

步桐也改了B的wait()——加了超时。将LOCK.wait()改成LOCK.wait(5000)。五秒超时。

wait的语义——线程释放锁，进入等待集。超时到达后——线程自动从等待集退出，重新尝试获取锁。获取锁后，从wait()方法返回，继续执行后续代码。

步桐在wait()调用后加了一个循环。循环体在每次wait()返回后检查条件是否真正满足。这是wait/notify协作模型的标准安全模式。

"为什么要循环？"

"两个原因。"步桐说，"第一——虚假唤醒。操作系统在某些情况下会唤醒等待的线程，即使没有notify()调用。被虚假唤醒的线程必须重新检查条件——条件不满足就继续等。第二——线程在wait()返回后，不能假设被通知的条件仍然有效。从wait()返回到线程重新获得锁之间——可能有另一个线程获取了锁并修改了条件。"

步桐在B的代码里写：synchronized (LOCK) { while (buffer.isEmpty()) { LOCK.wait(5000); } }。

"A通知了B，B就能醒。A没通知——B最多等五秒，自动醒。"

## 五

步桐把改动部署到B的工位。B的线程状态监控面板上——WAITING持续时间从两小时变成了一到三秒。B偶尔在缓冲区为空时进入TIMED_WAITING，然后在五秒内被A的notify()唤醒——也可能超时后被原子变量唤醒。

但步桐注意到了notify()和notifyAll()的选择。

B查看了当前的设计——车间里只有一个B——每个装配线只有一个运输线程。理论上用notify()就够了——只唤醒一个等待线程。但步桐改用了notifyAll()。

"为什么不用notify()？"主管问。

"notify()唤醒任意一个等待线程。"步桐说，"如果车间里有多个线程在LOCK上等待——比如另一个检测线程也在等LOCK——notify()可能唤醒的是检测线程而不是B。检测线程被唤醒后发现条件不满足，再次进入等待集。B没被唤醒——继续等。notifyAll()唤醒所有等待线程——每个线程独立检查自己的条件——满足条件的那个线程继续执行，不满足的重新等待。"

"那如果只有B一个等待线程呢？"

"即使只有一个等待线程——notify()也可能触发问题。"步桐说，"某些JVM实现中，notify()唤醒线程的顺序不可预测——优先级、调度策略、CPU架构都可能影响唤醒顺序。notifyAll()没有这个不确定性。notifyAll()的开销确实略大于notify()——唤醒所有等待线程比唤醒一个要调用更多的线程调度操作。但在99%的场景中，notifyAll()的安全优势远超这个开销差别。"

步桐在车间协作规范上又加了一行："优先使用notifyAll()——除非经过严格的性能评估确认notify()不会导致线程饿死。"

她同时在规范上追加了一条关于管程(Monitor)使用的内容——wait/notify/notifyAll全都属于JVM管程的一部分。管程的核心理念：同一时间只有一个线程可以执行管程内部的方法，线程通过条件变量等待特定条件满足，满足条件后重新进入管程。wait/notify正是管程条件变量的实现。

"管程的好处？"主管问。

"把锁和条件变量放在同一个对象里。"步桐说，"不分开管理——就不会出现'锁对象A配条件变量B'这样的混乱。管程就是synchronized加wait/notify——同一个对象同时提供互斥和协作能力。"

## 六

步桐走出北五车间。天色已经从凌晨的暗紫变成了灰白。

B的工位正在正常运转。显示器上的零件被处理后有序流转。WAITING状态偶尔出现——但在五秒内自动恢复。A的轮询仍然在跑——但步桐把sleep时间从1000毫秒降到了500毫秒，同时加了条件判断：只有A确实在前三道工序之后才启动轮询——避免了不必要的CPU消耗。

主管关掉了车间面板上的应急标记。

步桐回到车间门口，在协作面板上留下了规范更新记录：

"wait()必须在条件检查的循环中——防止虚假唤醒。wait()必须设置超时——防止永久等待。notify()或notifyAll()必须由持有锁的线程调用——防止IllegalMonitorStateException。优先使用notifyAll()——防止线程饿死。wait/notify的锁对象必须与synchronized的锁对象一致——防止跨对象协作失效。"

规范的底部，步桐加了一行自己的话："等待不是休眠——等待是让出资源。让出资源的前提是不让人永远等下去。"

北五车间不是最后一个问题车间。步桐知道——并行城里还有更多协作问题。有些线程在轮询中空转，有些在等待集中永远沉睡。但至少北五修好了。A和B的协作协议被完整确立——统一锁对象、条件检查循环、超时退出、notifyAll唤醒。

在车间深处，B的线程正在缓冲区和装配线之间来回运输零件——偶尔等待，从不死等。
