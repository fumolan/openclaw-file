# 第23章：散落的拼图

## 一

步桐在西四车间遇到了一个问题——CountDownLatch和CyclicBarrier组合使用时——栅栏未创建就到达。

西四车间的流程——第一阶段需要等待三个线程完成初始化——使用CountDownLatch。第二阶段需要三个线程同时开始——使用CyclicBarrier。问题在于——第一阶段的一个线程在CountDownLatch减到零之前——就开始创建CyclicBarrier——导致其他线程到达时——栅栏还没有创建——抛出IllegalStateException。

"协作原语的组合使用——顺序和时序必须精确。"步桐说。

步桐调出代码——线程A在初始化完成后——创建了CyclicBarrier实例——然后countDown()。线程B和线程C在初始化完成后——调用countDown()——然后调用barrier.await()。时序问题——线程A创建CyclicBarrier的距离——(await的计数)时间零点不一致。

"协作流程需要明确的时序控制。"步桐在面板上画出了正确顺序——第一阶段——所有线程调用countDown()——CountDownLatch减到零——主线程被唤醒——创建CyclicBarrier。第二阶段——主线程通知所有线程——所有线程调用barrier.await()——等待其他线程到达——同时开始。

"协作原语的正确组合——同步创建——同步到达。"

## 二

步桐修改了西四车间的代码——

第一步——CountDownLatch初始化——所有线程完成初始化后——countDown()——主线程await()等待。

第二步——主线程被唤醒后——创建CyclicBarrier——通知所有线程准备就绪。

第三步——所有线程收到通知——调用barrier.await()——等待其他线程到达。

第四步——所有线程到达栅栏——同时开始第二阶段。

"核心原则——栅栏的创建必须在所有线程到达之前完成。"步桐说。"如果栅栏还未创建——线程到达——抛出IllegalStateException。"

步桐使用了双重通知机制——CountDownLatch用于等待初始化完成——另一个CountDownLatch用于等待栅栏创建完成。

代码结构：

// 主线程
initLatch.await(); // 等待所有线程初始化完成
barrier = new CyclicBarrier(3); // 创建栅栏
barrierReadyLatch.countDown(); // 通知所有线程栅栏已创建

// 工作线程
initLatch.countDown(); // 初始化完成
barrierReadyLatch.await(); // 等待栅栏创建
barrier.await(); // 到达栅栏

"双重通知——保证时序正确。"

## 三

步桐分析了CountDownLatch和CyclicBarrier的本质区别。

"CountDownLatch——一次性门闩——计数减到零后不可重置。"步桐说。"适用于等待一组事件完成——一个或多个线程等待其他线程完成初始化——等待多个服务启动——等待多个任务完成。"

"CyclicBarrier——可循环栅栏——所有线程到达后重置——可重复使用。"步桐说。"适用于多个线程在某个点同步——等待其他线程到达——到达后一起继续下一轮。"

"CountDownLatch——等待事件——事件完成后继续。CyclicBarrier——等待线程——线程到达后一起继续。"

步桐举例——CountDownLatch——火箭发射倒计时——十个检查项全部完成——火箭发射。CyclicBarrier——跑步比赛起跑线——十个运动员全部到达起跑线——同时起跑。

"语义不同——使用场景不同——组合使用时必须理解各自的语义。"

步桐在西四车间的规范面板上写下："CountDownLatch——等待事件。CyclicBarrier——等待线程。组合使用时——栅栏的创建必须在栅栏的到达之前——否则抛出IllegalStateException。双重通知机制——保证时序正确。"

## 四

步桐继续分析协作原语的组合——Phaser。

"Phaser——更灵活的栅栏——支持动态注册和注销线程。"步桐说。"CountDownLatch和CyclicBarrier——线程数固定——创建时指定。Phaser——线程数可动态变化——register()注册——arriveAndDeregister()注销。"

步桐检查了西四车间的线程数——固定三个线程——不需要Phaser的动态能力。但步桐在规范中记录了Phaser的使用场景——线程数动态变化的协作场景。

"Phaser还支持多阶段同步——每完成一个阶段——所有线程等待——然后继续下一阶段。"步桐说。"CyclicBarrier也支持多阶段——但Phaser的阶段计数更灵活——可以动态改变等待的线程数。"

步桐在协作原语对比表中补充了Phaser——

CountDownLatch——一次性——等待事件——计数减到零——不可重置。
CyclicBarrier——可循环——等待线程——线程全部到达——自动重置。
Phaser——可循环——等待线程——动态注册——多阶段——灵活但复杂。

"选择协作原语——根据场景需求——一次性还是可循环——固定线程数还是动态——单阶段还是多阶段。"

## 五

步桐完成了西四车间的协作原语组合问题修复——时序正确——栅栏在所有线程到达之前创建——双重通知机制保证同步。

他在工作日志上写下协作原语组合的最佳实践：

"协作原语的组合——需要明确的时序控制。创建在到达之前——通知在等待之后。双重通知——一个原语等待事件完成——另一个原语通知栅栏已创建——保证时序正确。"

"CountDownLatch——一次性——等待事件——适用于等待一组任务完成。CyclicBarrier——可循环——等待线程——适用于多线程同步点。Phaser——动态——多阶段——适用于线程数变化的场景。"

"协作原语的本质——同步点——线程在某个点等待其他线程——一起继续。不同的原语——不同的同步语义——不同的使用场景。理解语义——才能正确使用。"

步桐走出西四车间——协作原语的组合不再是问题——线程按照正确的时序执行——第一阶段完成——栅栏创建——所有线程到达——第二阶段同时开始。协作——不是简单的同步——是正确的顺序——正确的时序——正确的组合。
