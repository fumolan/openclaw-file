# 第21章：刻在石头上

## 一

阮钴在北六车间看到了一个现象——共享对象被多个线程同时修改——数据不一致。但阮钴没有像之前那样增加锁——而是选择了另一种方案——不可变对象。

"不可变对象——创建后状态不可改变。"阮钴说。"没有修改——就不需要锁——没有并发问题。"

北六车间的场景——一个配置对象——存储了生产线的参数。多个线程读取配置——偶尔有线程需要更新配置。之前的实现——配置对象是可变的——更新配置时修改对象的字段——多个线程同时读取和修改——数据不一致。

阮钴的方案——将配置对象改为不可变对象。配置对象的所有字段都是final的——构造时赋值——之后不可修改。更新配置时——创建新的配置对象——新的配置对象包含新的参数值——将引用指向新的对象——而不是修改原对象的字段。

"不可变对象——天生线程安全。"阮钴说。"没有修改操作——不需要锁——不需要同步——多个线程可以安全地同时读取。"

## 二

阮钴改造了北六车间的配置对象。

之前的实现：

public class Config {
    private int param1;
    private String param2;
    
    public void setParam1(int value) { this.param1 = value; }
    public void setParam2(String value) { this.param2 = value; }
    public int getParam1() { return this.param1; }
    public String getParam2() { return this.param2; }
}

改造后的实现：

public final class Config {
    private final int param1;
    private final String param2;
    
    public Config(int param1, String param2) {
        this.param1 = param1;
        this.param2 = param2;
    }
    
    public int getParam1() { return this.param1; }
    public String getParam2() { return this.param2; }
}

所有字段都是final的——类是final的——没有setter方法——只有getter方法。更新配置时——创建新的Config对象——config = new Config(newValue1, newValue2)。原对象保持不变——新对象包含新值——引用从原对象切换到新对象。

"不可变对象的创建——构造时赋值——之后不可修改。"阮钴说。"更新操作——不是修改对象——是创建新对象。"

## 三

阮钴进一步分析——不可变对象的引用切换需要保证可见性。多个线程读取配置——配置引用存储在一个共享变量中——更新配置时——需要将对新配置对象的引用写入共享变量——其他线程需要看到新的引用——而不是旧的引用。

"引用切换——需要volatile保证可见性。"阮钴说。

他使用了volatile引用：

private volatile Config config;

更新配置时——config = new Config(newValue1, newValue2)。volatile写操作——保证新对象的引用对其他线程可见。其他线程读取配置时——Config current = config。volatile读操作——保证读到的是最新的引用——而不是缓存的旧引用。

"不可变对象配合volatile引用——线程安全——无锁——高性能。"阮钴在面板上写。"不可变对象不需要锁——volatile引用保证引用的可见性——两者结合——实现无锁的线程安全。"

阮钴对比了之前的方案——可变对象加锁。读取配置时需要获取锁——更新配置时需要获取锁——锁的开销在高并发读取场景下显著。不可变对象方案——读取配置不需要锁——直接读取volatile引用——无锁——高性能。

"读多写少的场景——不可变对象加volatile引用——最优方案。"阮钴说。

## 四

阮钴继续分析——不可变对象的设计原则。

"所有字段final。"阮钴说。"final保证字段在构造完成后不可修改。如果字段是引用类型——引用不可修改——但引用的对象可能是可变的——需要确保引用的对象也是不可变的。"

"类final。"阮钴说。"final类不能被继承——防止子类添加可变字段或覆盖方法——保证不可变性。"

"构造时不要溢出this引用。"阮钴说。"构造函数中不要将this引用传递给其他对象——否则其他对象可能在构造完成前访问到未完全构造的对象——破坏不可变性。"

阮钴看到北六车间的配置对象——字段都是基本类型和String——String是不可变的——符合不可变对象的要求。如果字段是集合类型——需要使用不可变集合——Collections.unmodifiableList()或Java 9+的List.of()——创建后不可修改。

"不可变对象的所有字段——必须是不可变的类型——或者不可变的包装。"阮钴补充。"如果字段是可变类型——需要在构造时创建不可变的副本——或者在getter方法中返回不可变的视图。"

## 五

阮钴完成了北六车间的不可变对象改造——配置对象改为不可变——配合volatile引用——无锁——线程安全——高性能。

他在工作日志上写下不可变对象的设计原则和使用场景：

"不可变对象——创建后状态不可改变——天生线程安全——不需要锁——不需要同步。设计原则——所有字段final——类final——构造时不溢出this引用——字段类型不可变。"

"不可变对象配合volatile引用——读多写少场景的最优方案。写操作——创建新对象——切换引用。读操作——无锁——直接读取volatile引用。"

"不可变对象的优点——线程安全——无锁——高性能——易于理解——易于测试。不可变对象的缺点——每次更新创建新对象——内存开销——对象创建开销。频繁更新的场景——不适合用不可变对象。"

"String是典型的不可变对象——Java的核心类——线程安全——不需要锁。Java 9+的List.of()、Set.of()、Map.of()——不可变集合——线程安全——不需要锁。"

阮钴走出北六车间——配置对象的读取操作不再需要锁——多个线程并发读取——配置的引用在更新时切换——volatile保证可见性——读取线程要么读到旧配置——要么读到新配置——不会读到不一致的状态。

不可变——不是什么都不变——而是对象本身不变——引用可变。阮钴在想——如果整个系统的所有共享对象都是不可变的——并发问题就不会存在了。但这不现实——有些对象必须可变——有些场景更新频繁——不可变方案的内存开销不可接受。但至少——在适合的场景下——不可变对象是最简单、最安全的方案。
