# 第24章：有限共享

## 一

程锁在北七车间发现了一个问题——Semaphore控制资源访问时——高优先级线程被低优先级线程阻塞。

北七车间的场景——三个共享资源——使用Semaphore(3)控制并发访问。线程分为高优先级和低优先级——高优先级线程处理紧急任务——低优先级线程处理常规任务。问题在于——三个资源被低优先级线程占用——高优先级线程到达——没有资源可用——高优先级线程被阻塞——等待低优先级线程释放资源。

"优先级反转。"程锁说。

高优先级线程应该优先获取资源——但Semaphore的FIFO队列——线程按到达顺序排队——不考虑优先级。低优先级线程先到达——占用资源——高优先级线程后到达——等待低优先级线程。

"Semaphore不感知线程优先级——只感知获取许可证的顺序。"程锁在面板上解释。"非公平模式——线程竞争获取许可证——可能高优先级线程更早到达——获取许可证。公平模式——线程按队列顺序获取许可证——高优先级线程可能排在低优先级线程后面。"

程锁查看北七车间的Semaphore配置——公平模式。new Semaphore(3, true)。公平模式——线程按队列顺序获取许可证——高优先级线程被低优先级线程阻塞。

"公平模式——避免饥饿——但导致优先级反转。"程锁说。

## 二

程锁分析了Semaphore的公平和非公平模式。

非公平模式——线程获取许可证时——先尝试获取——获取成功则立即获得——获取失败则进入队列等待。优点——吞吐量高——获取成功不需要进入队列。缺点——可能饥饿——新到的线程可能抢先获取——队列中的线程可能长时间等待。

公平模式——线程获取许可证时——先检查队列——队列为空则获取——队列不为空则进入队列等待。优点——避免饥饿——按顺序获取。缺点——吞吐量低——每次获取都要检查队列——高优先级线程可能排在低优先级线程后面。

"公平和非公平——不是优先级的公平——是获取顺序的公平。"程锁说。"优先级反转——Semaphore不感知线程优先级。"

程锁考虑了几种解决方案——

方案一——使用非公平模式。高优先级线程到达时——直接尝试获取——可能成功——减少等待时间。但非公平模式可能导致低优先级线程饥饿。

方案二——使用PriorityBlockingQueue代替Semaphore。线程按优先级排队——高优先级线程先获取资源。但PriorityBlockingQueue不提供许可证管理——需要自己实现资源分配逻辑。

方案三——使用可中断的获取操作。高优先级线程获取许可证时——使用tryAcquire(timeout)——超时后采取其他策略——如创建临时资源、借用资源、拒绝低优先级线程。

## 三

程锁选择了方案三——tryAcquire(timeout)配合优先级队列。

高优先级线程——tryAcquire(100, TimeUnit.MILLISECONDS)——超时时间内尝试获取许可证——获取成功则执行任务——超时则进入优先级队列等待。

优先级队列——存储等待的高优先级线程——低优先级线程释放许可证时——检查优先级队列——队列不为空则通知高优先级线程获取许可证。

代码示例——

Semaphore semaphore = new Semaphore(3, true);
PriorityQueue<Thread> highPriorityQueue = new PriorityQueue<>();

// 高优先级线程
boolean acquired = semaphore.tryAcquire(100, TimeUnit.MILLISECONDS);
if (!acquired) {
    highPriorityQueue.offer(Thread.currentThread());
    semaphore.acquire(); // 进入队列等待
    highPriorityQueue.remove(Thread.currentThread());
}

// 低优先级线程释放许可证时
semaphore.release();
if (!highPriorityQueue.isEmpty()) {
    // 通知高优先级线程
}

"优先级队列辅助Semaphore——实现优先级感知的资源分配。"程锁说。"但实现复杂——需要额外的同步机制——保证优先级队列的一致性。"

程锁意识到——优先级反转不只是Semaphore的问题——是所有共享资源分配机制的问题。锁、信号量、资源池——都可能出现优先级反转——高优先级线程等待低优先级线程释放资源。

"优先级反转的根本原因——资源竞争——高优先级线程和低优先级线程竞争同一资源。"程锁说。"解决优先级反转——要么资源不共享——要么优先级继承——要么优先级感知的资源分配。"

## 四

程锁在北七车间实现了tryAcquire(timeout)方案——高优先级线程使用tryAcquire()——非公平模式——尝试获取许可证——获取成功则立即执行——获取失败则等待。低优先级线程使用公平模式——进入队列等待。

"高优先级线程——tryAcquire()——可能获取成功——减少等待时间。低优先级线程——公平模式——按顺序获取——避免饥饿。"

程锁测试了改造后的效果——高优先级线程的平均等待时间从两百毫秒降低到五十毫秒。低优先级线程的平均等待时间略有增加——从五十毫秒增加到八十毫秒——但整体可接受。

"高优先级线程的等待时间减少——优先级反转的影响降低。"程锁说。"但没有完全消除优先级反转——只是降低影响。"

程锁在规范面板上写下Semaphore的使用建议——

"Semaphore控制资源的并发访问数量——不感知线程优先级。非公平模式——吞吐量高——可能饥饿。公平模式——避免饥饿——可能导致优先级反转。高优先级场景——使用tryAcquire(timeout)——减少等待时间——或实现优先级感知的资源分配机制。"

## 五

程锁完成了北七车间的Semaphore优先级反转问题修复——高优先级线程使用tryAcquire()——低优先级线程使用公平模式——优先级反转的影响降低。

他在工作日志上写下Semaphore的使用心得：

"Semaphore——许可证管理——控制资源的并发访问数量。获取许可证——acquire()或tryAcquire()。释放许可证——release()。acquire()阻塞直到获取许可证——tryAcquire()立即返回或超时后返回。"

"公平和非公平——选择取决于场景。吞吐量优先——非公平模式。避免饥饿——公平模式。高优先级线程——tryAcquire()减少等待。"

"优先级反转——高优先级线程等待低优先级线程释放资源——Semaphore不感知优先级。解决优先级反转——资源隔离——高优先级资源和高低优先级资源分开。优先级继承——低优先级线程持有资源时临时提升优先级——Java不直接支持。优先级感知——实现自己的资源分配机制——考虑线程优先级。"

程锁走出北七车间——Semaphore的许可证在非公平模式下被高优先级线程快速获取——在公平模式下按顺序分配——优先级反转的问题缓解但未完全消除。优先级反转是共享资源竞争的本质问题——资源有限——竞争无法避免——只能设计机制降低影响。
