# 技术知识写小说规则

将以下内容嵌入写作上下文，作为固定规则块。

## 核心规则：技术不是知识，是工具

技术知识在小说中的唯一作用是：帮助角色解决问题或制造问题。
不能作为"知识展示"存在。

## 基本信息
 - 小说保存在：~/vovel/{小说名称}
 - GitHub仓库：fumolan/openclaw-file（master分支，novel/{小说名称}/目录）
 - 字数要求： 中篇小说（约6-20万字）
 - 每次写一个完整章节，约2500-4000字

## 工作流程
1. 读取novel_source.sql文件或者数据库中novel_source表中的input_path 和course_path数据
2. 使用git工具下载input_path仓库中的文件到 ~/.openclaw/workspace/novel/中
3. 用 read 工具读取  ~/.openclaw/workspace/novel/{course_pat} 目录下文件以及子目录下文件作为写小说的技术素材。
4. 根据技术内容适配故事类型：古典武侠、玄幻修仙、机械世界、言情虐恋、架空历史、机器觉醒、太空遨游、星际旅行、海底探险、极限挑战、都市异能、末日求生、赛博朋克、校园推理、金融暗战、医疗悬疑
5. 生成大纲，必须包含：
   - 标题与类型
   - 世界观（200-400字）
   - 主要人物（7-13个，性格必须鲜明张扬，每个角色要有独特的说话风格和行事逻辑，拒绝脸谱化）
   - 核心设定（7个以上技术具象化元素）
   - 剧情大纲 （500字以内）
   - 章节规划（20-40章，每章标题+150-200字情节+技术融入+悬念，总字数控制在20万字以内）
   - 技术知识点覆盖表
   - 写作风格
6. 更新数据库或者把相关更新语句写入到 novel_source_update.sql文件中：
UPDATE novel_outline SET title='标题', genre='技术领域 × 故事题材', outline='完整大纲Markdown',chapter_num= {根据大纲生成的章节数量}, current_status='completed' WHERE id=XX;
只改 title、genre、outline、current_status，chapter_num 不动 input_path 和 course_path。


### 注意
- 每次只处理一条记录
- 章节规划20-40章，每章描述精简，避免超时
- 人物性格要张扬鲜明，有独特的语言风格和行为逻辑
- 超时的留在 processing，下次重试



### 判断标准

- ❌ 去掉这段技术内容后剧情还能走 → 删除，这是注水
- ✅ 去掉后主角无法解决问题 → 保留，这是剧情

## 三重投射检查表

每融入一个技术概念，检查它在故事中是否有以下三层：

1. **表层**：主角用这个技术解决了什么具体问题？
2. **中层**：这个技术的机制对应了什么剧情隐喻？
   - 例：GC回收 = 文明的记忆被丢弃
   - 类加载 = 文明的起源和继承
   - 死锁 = 无法调和的冲突
3. 不需要每章都有，但整体要用这个隐喻串起来

## 禁用词清单

写作时禁用以下句式——出现一条即为AI痕迹：

- ❌ "简单来说，X就是……"
- ❌ "X的原理是……"
- ❌ "X是一种……的机制"
- ❌ "举个例子，X相当于……"
- ❌ "我们通常把X分为……"
- ❌ "X的核心思想是……"
- ❌ 任何以"X是"开头、接下来做名词解释的句子

## 替代公式

**[危机/故障] + [主角看到/听到/感受到异常] + [主角操作] + [结果]**

模板句式：

- 禁用： "GC算法分为标记-清除、标记-整理和分代收集。"
- 可用： "系统卡了。不是网络延迟——是Full GC。陆辰知道这意味着什么：老年代满了。他还有一次机会，必须在下一轮STW到来之前找到那批泄漏的对象。"

## 技术融入通用公式

### 第一步：把概念翻译成故障

- "JVM内存分区" → "堆爆了"
- "类加载" → "Jar包打不开"
- "死锁" → "系统卡死"
- "CAS" → "数据写错了"
- "NIO" → "通信断了"

### 第二步：把解释变成动作

旁白 "X的工作原理是Y"
→ 主角做了一件事，读者看到结果，自己脑补原理

### 第三步：把概念变成操作按钮

主角做了什么操作 → 系统反馈了什么 → 成功了还是失败了

例：陆辰敲下jstack → 终端吐出线程栈 → 他看到了两个线程互相等待
读者不需要懂 jstack 是什么——看到输出就知道了

## 口语化检查

写完后用下面尺度自检：

读一段的时候问自己：

- 像不像老师在讲课？ → ❌ 重写
- 像不像工程师在修服务器时的自言自语？ → ✅ 合格
- 能不能删掉50%的技术细节而不影响剧情推进？ → ❌ 注水太多，删

## 技术准确性约束

- 每个技术知识点必须有真实依据
- 必须在技术社区（StackOverflow、Java规范、官方文档）中存在对应的真实概念
- 不可以为了剧情需要捏造不存在的JVM行为
- 可以简化（省略细节）但不可以错误（违反基本原理）
