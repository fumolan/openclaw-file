# 第22章 迷惑的颜色

季西正在调试一个新的GC方案——ZGC。

ZGC和之前用的G1完全不一样。G1把堆分成Region，而ZGC几乎对每一次对象访问都做间接处理。最核心的机制是指针染色——用指针里多余的位来存储GC状态信息。这是一种激进的创新设计，把GC状态直接编码到指针里，而不是用额外的标记位。

「你来看看这个。」季西指着屏幕上的一行错误日志，眉头紧锁。

展昭凑了过来。屏幕上显示着一个崩溃信息：Guarantee failure: Bad colored pointer 0x00007f3a8c012345。

「指针解码出错了。」季西说，「ZGC的染色指针在访问时被错误地解码了。这可不是小问题——一个错误的地址意味着访问到错误的内存，或者直接崩溃。」

「什么是染色指针？」展昭问，他对这个新机制还不熟悉。

季西拿出了一块白板画起来：「普通的Java对象引用是一个64位的地址。在64位系统中，我们只需要用其中48位来寻址——因为当前硬件只支持到48位虚拟地址空间。剩下的高位——比如48到63位——ZGC用来存储额外信息。」

「这就是染色？」

「对。ZGC把这16个高位中的4位用来存储颜色信息——比如这个对象是不是在重定位集中、是不是已经被转发过了。另外还有几位用来存储终结计数——用来处理finalizer。每个对象引用都带着自己的GC状态，这样就不需要额外的标记结构了。」

「那解码出错意味着什么？」

「意味着线程在读取引用时，从染色指针里提取的地址被污染了——得到的地址不是一个有效的对象地址。如果代码用这个地址去访问对象——就会导致Segmentation Fault。」

「是什么导致了染色指针被污染？」

季西调出了更多的日志：「看这里的流水——在并发标记过程中，ZGC会更新对象的颜色。如果某个线程在颜色更新正在进行的同时读取了这个指针——可能会读到半更新的颜色位。」

「半更新——也就是读到一个还没有完全写入的值？」

「对。ZGC的颜色更新没有使用全局同步。它依赖原子操作——但原子操作只保证单次读写的原子性，不能保证读到的值是最新值。在多核CPU上，一个核心写入的颜色更新可能还在缓存中，另一个核心读到的还是旧值。」

「那怎么修复？」

「需要插入内存屏障。」季西说，「在读取引用时防止CPU乱序——让染色指针的读取和颜色解码之间形成一种顺序关系——确保读取到的值已经完成了所有相关的写入。」

展昭想了想：「但ZGC的设计目标之一是低延迟，加入内存屏障会不会增加延迟？」

「会——但只是在染色指针读取时。这个操作对绝大多数引用来说不是每个循环都有的——它是GC屏障的一部分。ZGC使用了读屏障——当线程从堆中读取对象引用时，会触发一个读屏障来验证指针的颜色。」

季西在ZGC的源码中找到了染色指针读屏障的实现。他看到一段没有使用任何内存屏障的代码。「就是这里了。」他说，「在并发标记期间，更新对象颜色位之后没有插入StoreLoad屏障——导致其他线程读取时可能读到旧颜色。而他加上了关键的屏障代码，然后重新编译。」

「这样就能保证颜色更新对所有线程立即可见了？」

「对。代价是每次写入染色指针的开销增加了几个纳秒——但比让应用崩溃好。」

展昭在一旁看着：「ZGC看起来很美——几乎无停顿——但实现细节藏了无数这样的陷阱。」

「任何优秀的系统都是如此。」季西保存了修改，「表面越平滑，下面的螺丝就越密。染色指针是ZGC的核心创新，但也是最容易出问题的地方。」

季西刚修好了染色指针的读屏障问题，又有一个新的崩溃日志送到了他的桌上。

展昭拿着日志走进来：「又有一个ZGC相关的崩溃——这次不是在读屏障中——而是在GC线程的并发重定位过程中——一个对象被移动了——但发现它的引用还没有被更新。」

「这不可能——」季西说，「ZGC的并发重定位机制是这样的——当一个对象被选中需要移动时——GC线程把它复制到新地址——然后更新所有指向它的引用——最后释放旧地址的内存。」

「但如果更新引用的过程中——有一个应用程序线程同时在读取这个引用——」

「——那就需要用读屏障来处理——在读取时检测到对象被移动——然后通过转发表找到新地址——用新地址的值返回。」

「那崩溃的原因是什么？」

季西打开崩溃现场的日志：「看这个——重定位时——GC线程完成了对象的复制——但在更新引用的那一刻——应用程序线程正好在读同一个引用——读屏障检查了染色指针——发现指针的颜色标记为'已重定位'——于是去查转发表——但转发表中的条目已经被另一个线程移除了。」

「两个线程同时操作转发表——一个插入新条目——一个删除旧条目——导致了转发表的不一致？」

「更糟——」季西指着日志的一个角落，「转发表本身使用的是ConcurrentHashMap——理论上它是线程安全的——但ZGC对转发表的操作不是简单的put和remove——它需要在一个段落地处理多个相关的条目——比如一个对象的多个引用需要同时更新——而ConcurrentHashMap只保证单个操作的原子性——不保证跨条目的原子性。」

「所以如果GC线程在更新一个对象的所有引用——它需要在一个事务中完成所有更新——而ConcurrentHashMap无法提供这种事务语义。」

「对。所以我们需要一个更大粒度的锁——覆盖整个转发表的一个逻辑区段——在更新一个对象的所有引用期间——锁定这个对象在转发表中的所有条目——不让其他线程在这段时间内操作这些条目。」

季西在ZGC的源码中找到了转发表的操作部分——所有对转发表的访问都被封装在几个核心方法中。

「我需要给这些方法加上一个分段锁——把转发表分成若干个逻辑分片——每个分片使用一个独立的锁——在操作一个对象的引用时——只锁定该对象所在的分片——不影响其他分片的访问。」

展昭问：「那如果两个对象恰好落在同一个分片中——而它们同时被重定位——」

「它们会互相等待——一个重定位完成——解锁分片——另一个重定位开始。」

「那重定位的并发度不就降低了？」

「会降低一点——但总比崩溃好。」

季西在代码上修改了转发表的锁粒度——从无锁改为分段锁。

「加上内存屏障——加上分段锁——ZGC看起来不再那么'无停顿'了。」展昭说。

「它的目标是接近零停顿——不是真正的零停顿。」季西说，「所有的并发算法都有微观的阻塞——只是它们不在全局安全点阻塞整座城市——而是在单个数据的粒度上做微观等待。」

「微观等待比宏观暂停好一万倍。」

「一万倍——不夸张。」季西确认了修改，「希望这是ZGC的最后一个染色指针问题了。」

「——你确定你希望它是最后一个？」

季西笑了：「我当然知道——永远不会是最后一个。」


修复完转发表的分段锁之后，季西开始反思ZGC的整体设计哲学。

「ZGC追求的是超低暂停时间——目标是不超过10毫秒。为此它几乎做了所有能做的工作：并发标记、并发重定位、染色指针、读屏障——让GC的大部分工作与应用程序线程并行执行。」

「但代价是什么？」展昭问。

「代价是CPU开销——读屏障在每个对象引用读取时都会执行——即使是那些永远不会被GC访问的短期对象——读屏障还是会被执行。」

「那读屏障的性能开销有多大？」

「看CPU架构和引用模式——平均在每个引用读取时增加5-15%的开销。在CPU密集型的应用中——这是一个不可忽视的代价。」

「那和G1相比呢？」

「G1的写屏障比ZGC的读屏障轻量很多——但G1的停顿时间更长——在堆比较大的时候——G1的Mixed GC可能需要几百毫秒。而ZGC的停顿时间几乎不受堆大小影响——始终在10毫秒以内。」

「所以这是延迟和吞吐量之间的权衡——ZGC偏向低延迟——G1偏向高吞吐量。」

「对。但还有第三个维度——堆大小。当堆超过100GB时——G1的停顿时间会显著增加——可能超过1秒。而ZGC的停顿时间几乎保持不变——对超大堆来说——ZGC是更好的选择。」

「那对于我们的场景——堆是2GB——」

「2GB——用G1也行——用ZGC也行。但ZGC的低延迟优势在2GB堆上并不明显——因为G1在2GB堆上的停顿时间也不到100毫秒——在大多数应用中——100毫秒的停顿是可以接受的。」

「那ZGC更适合哪类应用？」

「超大堆应用——比如内存数据库、大型缓存系统、实时交易系统——堆超过32GB甚至100GB——G1的停顿时间会变得不可接受——而ZGC仍然能保持在10毫秒以内。还有延迟敏感类应用——比如在线游戏、高频交易——任何超过10毫秒的停顿都可能导致服务质量下降。」

季西调出了一张决策树：

「堆小于4GB → G1（或者Serial/Parallel——取决于延迟要求）
堆4-32GB → G1（延迟容许）或ZGC（延迟敏感）
堆大于32GB → ZGC（或Shenandoah）」

「所以对我们2GB的堆来说——G1已经足够了。ZGC的染色指针问题和复杂的并发机制带来的收益并不明显。」

「但ZGC是我们未来大规模堆的探路者——」季西说，「今天我们在2GB的堆上调试ZGC——明天当我们的堆扩展到几十GB时——这些调试积累的经验就是我们的财富。」

展昭点了点头：「所以现在修理染色指针——不仅是为了解决眼前的问题——更是为了未来做准备。」

「对。每修复一个染色指针的问题——就少一个潜在的线上事故。」季西合上了日志，「迷惑的颜色——就像那部老电影里的秘密代码——看起来是一个数字——但实际上藏着整座城市所要的一切信息。只要解码对了——一切都好。解码错了——城市就会走向崩溃。」
