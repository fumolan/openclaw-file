# 第22章 迷惑的颜色

季西正在调试一个新的GC方案——ZGC。

ZGC和之前用的G1完全不一样。G1把堆分成Region，而ZGC几乎对每一次对象访问都做间接处理。最核心的机制是指针染色——用指针里多余的位来存储GC状态信息。

「你来看看这个。」季西指着屏幕上的一行错误日志。

展昭凑了过来。屏幕上显示着一个崩溃信息：

```
Guarantee failure: Bad colored pointer 0x00007f3a8c012345
```

「指针解码出错了。」季西说，「ZGC的染色指针在访问时被错误地解码了。」

「什么是染色指针？」展昭问。

季西拿出了一块白板画起来：「普通的Java对象引用是一个64位的地址。在64位系统中，我们只需要用其中48位来寻址——因为当前硬件只支持到48位虚拟地址空间。剩下的高位——比如48到63位——ZGC用来存储额外信息。」

「这就是'染色'？」

「对。ZGC把这16个高位中的4位用来存储颜色信息——比如这个对象是不是在重定位集中、是不是已经被转发过了。另外还有几位用来存储终结计数——用来处理finalizer。」

「那解码出错意味着什么？」

「意味着线程在读取引用时，从染色指针里提取的地址被污染了——得到的地址不是一个有效的对象地址。如果代码用这个地址去访问对象——就会导致Segmentation Fault。」

「是什么导致了染色指针被污染？」

季西调出了更多的日志：「看这里的流水——在并发标记过程中，ZGC会更新对象的颜色。如果某个线程在颜色更新正在进行的同时读取了这个指针——可能会读到半更新的颜色位。」

「半更新——也就是读到一个还没有完全写入的值？」

「对。ZGC的颜色更新没有使用全局同步。它依赖原子操作——但原子操作只保证单次读写的原子性，不能保证读到的值是'最新'的。」

「那为什么以前没问题？」

「因为ZGC假设运行时能正确地从染色指针中提取地址和颜色的组合。但如果对象在并发移动过程中——它的地址变了——这需要ZGC的内存转发表做一次额外的查找。」

「我听着像是CPU的乱序执行导致的问题？」

「可能是。」季西说，「CPU在执行指令时可能会把读取染色指针的指令提前——在颜色更新完成之前就读到了指针内的值。然后解码出错误的地。」

「那怎么修复？」

「需要插入内存屏障。」季西说，「在读取引用时防止CPU乱序——让染色指针的读取和颜色解码之间形成一种拜伦关系——确保读取到的值已经完成了所有相关的写入。」

展昭想了想：「但ZGC的设计目标之一是低延迟，加入内存屏障会不会增加延迟？」

「会——但只是在染色指针读取时。这个操作对绝大多数引用来说不是每个循环都有的——它是GC屏障的一部分。ZGC使用了读屏障——当线程从堆中读取对象引用时，会触发一个读屏障来验证指针的颜色。」

「而这个读屏障正是ZGC延迟的源头之一。」

「是的。ZGC的大多数GC工作都是在读屏障里完成的——对象移动、重定向、标记。所以读屏障是ZGC的核心性能瓶颈。」

「那这次染色指针解码错误呢？是读屏障本身的问题，还是实现问题？」

「是一个边界情况。」季西说，「在极低概率下——当CPU在同一个缓存行上同时更新指针的多个字节时——读取操作可能会看到新旧值混合的结果。这不是ZGC特有的问题——所有并发算法都有这个风险。」

「需要用原子操作来更新染色指针。」

「对。用AtomicReference或者Unsafe的putLongVolatile——保证对64位值的写入是原子的。如果写了一半被中断——读到的要么是全旧值，要么是全新值——不会出现混合状态。」

「那当前的实现用了什么？」

「普通赋值操作——='——在64位JVM上64位赋值是原子的——但那只保证赋值本身是原子的。不能保证读到的就是最新值——因为CPU缓存可能不同步。」

「所以需要volatile？」

「对。或者加上内存屏障——在写入后插入StoreLoad屏障——在读取前插入LoadLoad屏障。」

季西在终端里打开了ZGC的源码，找到了染色指针读屏障的实现。他看到一段没有使用任何屏障的代码。

「就是这里了。」他说，「在并发标记期间，更新对象颜色位之后没有插入StoreLoad屏障——导致其他线程读取时可能读到旧颜色。」

他加上了关键的屏障代码，然后重新编译。

「这样就能保证颜色更新对所有线程立即可见了？」

「对。代价是每次写入染色指针的开销增加了几个纳秒——但比让应用崩溃好。」

展昭在一旁看着：「ZGC看起来很美——几乎无停顿——但实现细节藏了无数这样的陷阱。」

「任何优秀的系统都是如此。」季西保存了修改，「表面越平滑，下面的螺丝就越密。」
