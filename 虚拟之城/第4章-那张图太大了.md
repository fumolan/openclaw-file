# 第4章 那张图太大了

季西站在老年代入口处，看着Full GC的日志，瞳孔微微收缩。

担保机制启动后，大批未成年对象从Survivor区涌入老年代。年龄字段坏了的对象失去了晋升控制——它们被一股脑推了进来，像潮水冲过堤坝。现在老年代的一块连续区域里塞满了短命对象，大部分死亡只在一瞬间。清理它们需要一次Full GC。

Full GC启动，最慢的环节是对象图遍历。

季西的团队熟悉这个流程：从GC Roots出发往下走，每个活着对象都走一遍它的引用字段，遇到新对象就标记，继续往下。标记完成之后再做清扫。整个过程像一张渔网从海底拖过——你拉起网的每一寸都必须检查。如果水底有一块巨大的礁石，网拖过它的时候，整张网会卡住。

季西现在面对的就是这块礁石。

GC根扫描已经完成，根引用找到了三十七个直接存活的对象。标记器从这三十七个入口往下走——一个对象指向下一个，下一个指向下下个，像链条。大部分链条很快走完：一个栈帧引用一个String，String指向char数组，结束。三五个对象算一条小链。

但有一条链，季西盯着它看了五秒。

从根出发，首先指向一个ConcurrentHashMap实例。HashMap本身不大，但它的Entry数组指向了八个桶，每个桶里挂着一条链表。链表上的第一个Entry指向了另一个HashMap。第二个HashMap又指向了第三个。

季西顺着这条链往下点开。

第一层：HashMap。大小正常。
第二层：Entry -> HashMap。嵌套层。
第三层：Entry -> HashMap。再嵌套。
第四层：Entry -> HashMap。
第五层：Entry -> ArrayList。
第六层：ArrayList里的每个元素是一个Object数组。
第七层：Object数组里的每个元素又指向一个Map。
第八层：Map -> Entry -> Object。
……

季西没有停下来数。他直接从日志里提取了一个数值——深度。

对象图深度：127层。

Mark阶段每往下一层，就要从线程的工作队列里取一个新任务——处理当前对象的引用列表。如果引用列表很长，队列压力大。如果层数很深，队列里积压的任务会像滚雪球，每次分配新任务都有开销。127层意味着标记器要在这个对象图上递归折叠127次，才能走到链末端。

而且走到末端不代表结束——同一层可能有几十个兄弟节点，每一个又挂着自己的子图。这不是一条链，是一棵放眼望不到边的树。

季西调出这个对象的类型名：ApplicationContext。

Spring的上下文。应用程序启动的时候把整个配置模型都挂在这个对象上——所有的BeanDefinition、所有的单例Bean、所有的AOP代理链、所有的拦截器、所有的监听器——全部从这一个对象出发可到达。它不是一棵树，是一整片森林。

季西深吸一口气。

他见过大的对象图，没见过这么大的。一个Web应用启动后运行了三天，各种会话数据、缓存、懒加载的代理对象、事务管理器持有的连接池引用——全挂在这个上下文的引用树下。对象图的节点数，日志末尾给了一个估算值：

总存活对象数：约八百七十万。

其中大约七百万在这个上下文子树下面。

季西把笔放下，靠在椅背上，盯着天花板看了两秒。

然后坐直了。

「Full GC标记阶段，预计耗时——」季西对旁边的监控终端说了一句，终端弹出估算公式：平均每个对象标记耗时 × 对象总数 × 引用遍历系数。

「6.8秒。」

六点八秒的STW。整座城市全体线程挂起六点八秒。

季西站起来，走到标记队列的监控台前。他没有取消Full GC——取消也没用，老年代空间不够了，不做GC就等着内存溢出。他只是想看看，能不能在STW开始之前做点什么。

但STW已经开始。

秦哨卡那边已经发出了安全点请求，所有线程正在往安全点集结。季西不能取消全局暂停，不能跟时间讨价还价。

六点八秒。

标记器已经开始工作了：从GC Roots出发，遍历，标记，压入队列，继续遍历。

季西盯着那个ApplicationContext的标记进度。标记器从根出发，第一层花了0.2毫秒把三十七个根对象的引用全部压进队列。然后标记器取队列顶部的第一个任务——就是那个ApplicationContext。

第二层：ApplicationContext的内部引用。

BeanFactory。Environment。ResourceLoader。ApplicationStartup。LifecycleProcessor。

每一个引用又指向自己的子图。BeanFactory是最重的——它持有所有BeanDefinition的对象图，每个BeanDefinition又持有自己的ConstructorArgumentValues、PropertyValues、注解元数据、来源位置信息。单这一点，就衍生出数十万节点。

标记器在BeanFactory身上停留了大约四十毫秒——不是卡住了，是工作量太大了。四十毫秒处理了一个厂的Bean定义，然后继续往下翻。

第三层中间，标记器遇到一个Lazy-init的Bean，它的引用里有一个尚未初始化的代理对象——AOP生成的CGLIB代理。代理对象的引用链里有一个TargetSource，TargetSource指向实际的被代理Bean，被代理Bean又引用了它的依赖Bean。

这是一条跨层级的交叉引用。

季西看着标记器在这条交叉引用上绕了个弯——标记器维护着一个全局的"已标记"位图，遇到已经被标记过的对象就跳过。代理对象引用的实际Bean如果在之前的标记路径上出现过，就直接跳过，不会再走一遍。

但"不再走一遍"不代表不检查——它需要在位图里查一次这个对象有没有被标记过。位图是一块按比特位索引的内存，查一次是一个O(1)操作。但当节点数量以百万计，每个节点的引用字段数以十计——查位的操作次数膨胀得可怕。

季西看了一眼时间。1.7秒过去了。

标记器进度：处理了大约两百万个对象。还剩下六百七十万。

标记器在Level 47层遇到了一个巨大的ArrayList。ArrayList内部是一个Object[]，长度十八万。标记器需要遍历这十八万个元素，每一个元素要么是null，要么指向另一个对象。十八万的遍历不是问题——问题是这十八万个元素里有大约九万个不是null，每一非null引用都需要进一步展开。

九万个任务被塞进标记队列。

队列膨胀了。

队列膨胀的直接后果是内存压力——标记队列也是占用堆内存的。而堆内存本身就在被Full GC治理。标记队列膨胀意味着GC运行时的堆占用在一瞬间增加了数百KB，如果标记队列不受控地增长，它本身可能触发堆分配失败。

但标记器有硬性限制：队列深度上限和元素数量上限，压过线就会触发队列溢出——不做实时压缩就直接抛Concurrent Mode Failure。

季西盯着队列大小计数器。

1642。3804。7201。15129——

到20345的时候停了。标记器终于处理完那个ArrayList，队列开始消耗而不是堆积。数字缓慢回落。

季西吐出一口气。

四秒。

还剩。

标记进度：680万 / 870万。

季西扫了一眼那个ApplicationContext子树的进度。最大的那一坨——BeanFactory下面挂的Prototype范围——还没走到。Prototype Bean比Singleton Bean更棘手，因为它们没有缓存引用图，每次获取都可能生成新的引用结构。标记器走到Prototype区域的时候，某些对象图可能是运行态才构造出来的临时结构，GC看到的是一个冻结的快照，但冻结的快照里仍然保持了运行时的复杂度。

标记器触碰到Prototype区域。

队列数字又跳了一下。幅度不大——十五个新任务。但每个新任务的对象内部引用了旧任务的对象，形成了旧的标记队列里已经存在的对象和新的之间交叉引用。标记器不得不在新任务和旧任务之间来回跳转，读取引用，检查位图。

效率降低了大约三成。

「5.1秒。」

季西在心里数着。比预估多了零点儿几秒，因为Prototype区域的交叉引用导致cache miss率上升。标记器的读取模式从顺序读变成了随机读——在物理内存的随机位置上跳来跳去，缓存亲和性下降。

5.5秒。

5.8秒。

标记计数器：8,699,998。

最后两个对象。

6.0秒。

标记完成。

季西看了一眼挂钟。从安全点请求发出到标记完成，实际耗时6.0秒——比预估算的6.8秒少了一些，因为标记器在队列处理上做了一次动态的批量合并，减少了任务切换开销。

但六秒。

整座城市，所有线程，所有用户请求——全部暂停了六秒。

季西站起来，走到窗前。老年代的清扫阶段已经开始，死亡对象被标记为可回收，空间正在被整理。Full GC的收尾部分不需要STW了。

他转过身，拿起通讯器。

「秦哨卡，安全点释放。」

通讯器里传来秦哨卡确认的声音。所有挂起的线程开始从安全点恢复运行，程序计数器继续前进，用户请求继续处理。

六秒。对计算机来说像一个世纪。

但对季西来说，他还得面对一个更大的问题：这张对象图还会越长越大。如果下一次Full GC时，上下文的对象图长到一千万、两千万——那STW时间不会是一次性的。

它会线性增长。

季西看向老年代深处，那张还没处理完的对象图静静地躺在那里——八百七十万个节点，一个不能碰的庞然大物。
