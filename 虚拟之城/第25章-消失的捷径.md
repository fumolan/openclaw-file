# 第25章 消失的捷径

钱境的告警灯从没这么响过。

「CodeCache满了！」他对着对讲机吼道，「编译好的机器码不能再缓存了！」

白页和展昭以最快的速度赶到了钱境的办公室。控制台上，CodeCache的使用量停在了一个刺眼的数字：239.9MB。

「默认值是240MB。」钱境指着那个数字，「已经不能再大了。」

CodeCache——JVM用来缓存编译后机器码的存储区。C1和C2编译完一段方法的字节码之后，生成的优化机器码就放在这里。下一次调用同一个方法时，直接从CodeCache中取出机器码执行——不需要再编译，也不需要解释。

「如果满了呢？」白页问。

「满了之后——已经完成编译的代码可以继续使用——但新方法再触发编译时——不会再被写入CodeCache。后续调用那段方法——只能退回解释执行。」

「解释执行！」展昭脱口而出，「那性能会直接跳水。」

「不只跳水——是自由落体。」钱境调出了一张性能曲线图，「看——8分钟前CodeCache满了。之后的性能曲线从每秒12000次处理量掉到了每秒3000次——掉到四分之一。」

「哪些方法受影响最大？」

「所有在CodeCache满了之后首次被请求编译的方法。还有一些从CodeCache中被淘汰的旧编译版本——如果CodeCache用满了但没有淘汰旧条目——新条目根本无法进入。」

「那有淘汰机制吗？」

「CodeCache有——但它有自己的淘汰策略。默认是用最不常用的先淘汰。但有些常用的方法被误认为是'不常用的'——因为它们的调用频率在统计窗口内下降了。所以被淘汰的方法会在解释器中运行。但很快它们又需要被调用——需要重新编译——但CodeCache满了——于是形成了恶性循环。」

白页翻开CodeCache的规范文档：「CodeCache的问题根源是大小固定。但它不是堆——不能动态扩展。」

「那为什么不用更大的CodeCache？」

「因为CodeCache不是堆外内存，它是在JVM进程空间中的一个固定区域。如果设置过大——会挤占应用程序的内存空间。而且CodeCache是连续内存——操作系统在启动时分配给它固定大小的虚拟地址空间——不能事后扩大。」

「那现在怎么办？」

「手动触发CodeCache的清理。」钱境说，「让那些非可优化的代码——C1已废弃的版本——优先被淘汰。为C2新编译的版本腾出空间。」

他在控制台上输入了一条命令，让CodeCache扫地机器人模式启动——定期扫描并清理不再使用的编译代码。

但CodeCache的使用量只降了2MB。

「为什么只少了这么点？」白页问。

「因为大多数CodeCache里存的是还在频繁使用的代码。淘汰不了的。」

白页想了想：「那如果我们手动把一些方法降级呢？——强制让它们的编译层级从C2回退到C1——C1版本的机器码更小——虽然性能下降——但可以给C2方法让路。」

「可以。但需要识别哪些方法即使使用C1版本也不会影响整体性能。那些调用频率很高——但每个调用的内部逻辑很简单的——C2优化的效果不大。」

钱境在系统里做了一个统计：「分四类——高频复杂方法、高频简单方法、低频复杂方法、低频简单方法。我们把高频简单方法和低频复杂方法都标记为'不要C2'——让它们只走C1编译。保守估计可以腾出30%的CodeCache。」

他执行了批量标记。CodeCache的使用率从满格掉到了70%。

「现在有空间了。」他说。

很快，那些因为CodeCache满而退回解释执行的方法——重新被编译成了机器码。解释执行带来的拥堵慢慢消散了。

「CodeCache不是越大越好。」钱境看着回落的告警灯说，「但也不能太小。它像城市的快速路——每一次C1/C2编译都是一辆跑车——快速路堵了，跑车就只能降速到普通路上走。」

展昭在旁边记录着：「高频简单方法的识别标准是什么？方法体小于指定字节码大小——调用计数高于指定阈值——内联收益很低。」他在笔记本上写下了三个筛选条件。

白页提出了一个更根本的问题：「CodeCache满的根本原因——是编译方法太多——还是编译产物太大？」

「两个原因都有。」钱境指着统计面板，「最近一周系统引入了两个新框架——每个框架都注册了大量的动态代理类和Lambda表达式生成类——这些类的方法虽然简单——但数量巨大——每一个方法的编译产物都需要占用CodeCache空间。」

「动态代理类的特点——方法数量多——每个方法都很短——编译后机器码也很短——但架不住数量多。」

「那有没有办法让这些动态生成的短方法不进入CodeCache？」

钱境摇了摇头：「目前没有这个选项。CodeCache对编译后的代码是一视同仁的——不管代码是C1还是C2编译的——不管方法的复杂性——只要通过了编译阈值——就会被缓存。」

「那能不能在编译阈值上做文章？让短方法不触发编译？」

「可以调整编译阈值——提高触发编译的调用次数要求。但这样会影响所有方法——包括那些复杂的热方法也会延迟编译——整体性能下降。」

展昭拿着统计结果回来了：「CodeCache中占用最多空间的不是短方法——而是长方法的编译产物。前10%的长方法占用了CodeCache的60%。」

「那就更有理由限制长方法的内联膨胀——」钱境说，「——内联越多——编译产物越大。」

「但内联是性能优化的核心——」白页说，「——如果限制内联——性能会下降。」

「需要权衡。」钱境调整了一个参数，「把内联的内联深度上限从9层降到5层——可以减少内联导致的代码膨胀——同时保留最关键的性能收益。」

展昭进入了新的编译参数后重启了 hotspot 编译器：「CodeCache压力下降了——全量重新编译后——预估占用空间从240MB下降到180MB。」

「但性能呢？」

「基准测试显示——平均响应时间增加了3%——可以接受。」

「还有一件事——」白页说，「CodeCache的淘汰策略需要改进。现在是最不常用的先淘汰——但有些冷方法只是暂时冷——将来还会热——不应该被淘汰。」

「用热度衰减策略？」钱境问。

「对。把方法的调用计数随时间衰减——如果衰退到零——就淘汰。如果方法再次被调用——热度重新积累——不会被轻易淘汰。」

「这比现有策略更合理——不会因为统计窗口的偶然低谷就淘汰一个有用的方法。」

钱境在笔记本的最后写下了一张长期改进计划表：

Phase 1：动态CodeCache大小调整——允许在运行时扩展CodeCache——而不只是启动时固定大小。
Phase 2：分层CodeCache——C1和C2分别使用不同的Cache区域——可以单独调整。Phase 3：智能淘汰策略——基于热度衰减而非简单的命中率。

「但Phase 1和Phase 2需要改动JVM核心——」白页说，「——短期做不到。」

「那就从Phase 3开始。」钱境站起来伸了个懒腰，「每次告警——都是一次学习。CodeCache满了——学会了如何更好地管理编译产物的生命周期。」

展昭看着墙上挂着的代码生命周期图谱：「从解释执行到C1编译——到C2编译——到最后从CodeCache淘汰——每一步都有它的理由。」

「每一步也都有它的代价。」钱境说。

当晚，钱境收到了一份来自监控系统的报告——CodeCache的生命周期分析。

报告显示：编译后的代码在CodeCache中的平均存活时间是4小时。而那些被淘汰的方法——有40%在淘汰后的2小时内又重新触发了编译。

「这说明淘汰策略确实有问题——」钱境分析道，「——淘汰了不该淘汰的方法。」

他仔细研究了这40%的方法：它们有一个共同的特点——调用模式是周期性的。比如每小时的整点执行的定时任务——在整点前后被大量调用——在其他时间调用很少。当CodeCache压力大时——这些方法因为在统计窗口内调用少而被淘汰——但下一次整点来临时——它们又会被频繁调用——触发重新编译。

「这就是周期性方法的困境——」展昭说，「——它们的冷热是周期性的——而淘汰策略不看周期性。」

「解决方法是引入调用时间分布分析——」钱境说，「——如果方法在历史上有周期性的热点——就不会在低谷期被淘汰。」

「这需要记录每个方法的调用时间戳——开销太大。」

「可以简化——只记录方法的上次热点时间和热点周期——如果当前时间距离上次热点时间在一个周期内——就不淘汰。」

钱境在淘汰策略中加入了这个改进：「热点方法的保护窗口——如果一个方法在过去的热点周期内调用过——就保护它不在这个周期内被淘汰。」

再运行了一次模拟——重新编译率从40%下降到了15%。

「还有进步空间——但至少跳出了必然被淘汰又必然重新编译的死循环。」

白页走进来，手里拿着最新的参数确认书：「CodeCache的基础大小从240MB调整为192MB——预留48MB给动态扩展。如果192MB用满了——再申请扩展。」

「动态扩展终于要来了？」

「来了——但有限制。每次扩展最多12MB——最多扩展4次——最大不会超过240MB。这是操作系统和内存分配器的妥协——不是无限扩展。」

「总比固定的好。」钱境看着新的参数配置，「CodeCache——终于不再是一个塞满了就叫停的盒子了。」

「但它仍然是一条有尽头的路。」白页说，「只是尽头比原来远了一点。」

「只要尽头还没到——编译器就能继续为热点方法铺路。」钱境说。

展昭在笔记本上写道：「CodeCache的故事告诉我们——缓存永远不够用——永远是填满的。关键不是如何避免填满——而是填满时如何优雅地应对。」

「以及——」钱境补充道，「——如何让那些被打上'不常用'标签的方法——不会在下一个整点来临时悄无声息地消失。」
