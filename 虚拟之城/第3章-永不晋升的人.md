# 第3章 永不晋升的人

老堆站在Eden区门口，手里攥着一沓对象清单，眉头能夹死苍蝇。

这是他今天第三回核对新生代的存活对象了。第一次GC刚过，第二次GC也过了，第三次GC即将触发——但同一个对象，每次都在Eden区被标记为存活，每次都被复制到Survivor区，然后下一次GC又从Survivor活着回来，再被复制回去。

正常情况不说他也知道：一个对象在Eden区出生，第一轮Minor GC存活后进入Survivor区，年龄加1。此后每熬过一轮GC，年龄递增一次。当年龄涨到某个阈值——通常是15——就可以晋升到老年代。流程清楚，规则明确。

但这个对象，从第一次GC开始就不对了。

老堆把那个对象的记录调出来：Object_0x3F7A。类型是byte数组，大小48KB，出生在Eden区东南角。第一条记录显示Minor GC发生时它被标记为存活，复制到Survivor区。第二条记录显示下一次Minor GC——二十秒后——它又被标记为存活，又从Eden复制到Survivor。第三条一样。

但年龄字段一直是0。

老堆揉揉眼睛，又看了一遍。

年龄字段是对象头顶那行小字中的四位比特，藏在对象头的Mark Word里。Mark Word占据对象头的前八个字节，里面混着装了很多东西：哈希码、GC分代年龄、偏向锁的线程ID、锁标志位。四位的分代年龄写在Mark Word的特定比特位上，理论最大值15，每次熬过GC加1。

老堆把那个对象的Mark Word调成十六进制展开看。

0x00000000F88A2001。

他逐比特翻译：前八位是锁标志——无锁状态，普通对象。第57到60位——

四个零。

GC了三次，年龄还是四个零。

「你长生不老啊？」老堆嘟囔了一句。

他拿工具在Mark Word的年龄位上试着写了一个1。对象头是可改的，GC阶段写入年龄是标准操作。老堆写入，确认——然后退出工具，等第四轮Minor GC触发。

Eden区的清扫铃声响起。活的留下，死的清走。

铃响结束，老堆重新查看Object_0x3F7A的记录。对象被复制到了Survivor区，影子还在。

年龄字段：0。

他写入的1被清掉了。

老堆沉默了几秒。他退出GC工具，直接去翻这个对象的源。

对象的类型是byte[]，确实是一个普通的字节数组。但老堆发现了一个细节——这个对象的引用来源很复杂。它被三个不同的局部变量同时引用，两个栈帧各有一个槽位指向它，另外还有一个static字段指向同一个地址。三个引用指向同一块内存，每个GC Roots追踪路径都能找到它。只要有一个引用还活着，这对象就永远不会被标记为可回收。

「难怪你死不了。三个人拽着你呢。」

但年龄不加就不对了。GC标记存活对象后复制，复制过程中就应该同时更新年龄。就算三个引用都指向它，复制是复制，年龄是年龄，两者不冲突。老堆接上Survivor区的日志端口，把第四轮Minor GC的复制过程逐条读出来。

指令流显示：对象从Eden区被识别为存活——复制到Survivor区——更新年龄——完成。

逻辑没错。但年龄没变。

老堆把复制指令拆解成更细的微操作。复制产生了一个新副本，旧副本在Eden被回收。新副本应该继承旧副本的所有对象头信息，然后在GC过程中把年龄加1。正常流程是这样的：先拷贝对象体的所有实例字段，再拷贝对象头，然后修改Mark Word里的年龄位。

但复制指令只拷贝了Mark Word的前六十四位中的一部分。年龄位所在的四个比特——原封不动地从旧对象的Mark Word复制到了新对象的Mark Word，没有经过任何修改。而旧对象此时已经被GC标记为存活，它的年龄位本应该在上一次GC时加过——但因为某次对年龄的处理出了问题，旧对象的三次GC年龄都没变过。

不，更仔细地看——这根本不是旧对象的问题。

他盯着那行复制指令看了很久。指令本身是对的，复制对象头用的是整块拷贝。整块拷贝意味着Mark Word被整体搬到新对象里——包括年龄位。但Mark Word里的年龄位，在整块拷贝之前就已经是0了。而整块拷贝之后，没有任何子程序对那四个比特做chgAge操作。

复制指令本身就没连年龄更新的那一步。整个GC流程调用的子程序链里，末尾的年龄递增环节被跳过了。不是条件分支跳过——是压根没有那个指令。

「谁写的GC流程？」老堆问旁边的助理。

助理翻了翻日志：「上一次GC流程更新是三周前，季西队长亲自提交的变更。」

老堆放下清单，拿起茶杯喝了一口，然后站起来走向季西的办公室。

他路过Eden区的时候，瞥见Object_0x3F7A还在Survivor区里安稳地待着。第四次GC了，它还是零岁。像一个永远长不大的孩子，被三个家长死死拉住，困在新生代的循环里。Eden满了就搬到Survivor，Survivor满了就搬回Eden——反正老堆永远不知道它有多大了，因为它根本没长过岁数。

永远不晋升的后果，老堆很清楚。

Survivor区总有一天会被这些不晋升的常客塞满。然后GC算法会触发担保机制——把Survivor溢出的对象直接扔进老年代。但担保机制依赖年龄数据来判断哪些对象值得晋升、哪些该继续留在新生代。如果年龄全是零，担保机制等于蒙着眼睛做判断。要么全部晋升，老年代被未成熟对象撑爆；要么全部不晋升，Survivor溢出崩溃。

老堆敲了敲季西的门。

门里传来一声闷响，像是有人把一堆文件摔在了桌上。

「进来。」

季西的桌上堆满了GC日志。老堆走进来的时候他正在看一张三色标记图，手边是刚修好的一个Concurrent Mode Failure报告。抬起头看见老堆的表情，季西把笔放下了。

「说吧。」

「你三周前改的那个GC流程，」老堆说，「少了一行。」

季西愣了一下。

「什么少了一行？」

「年龄。复制的时候不加年龄了。」

季西的表情变了。不是惊讶——是困惑。他拿起手边一个记录本翻了翻，翻到某一页，手指停在那里。

「我没改过复制子程序。」季西说。「三周前的改动只修了Eden区的清扫触发条件，跟年龄那块隔了二十个模块。」

老堆盯着他。

「那谁改的？」

两人沉默了三秒。

季西放下茶杯，走到墙角一个监控终端前，敲了几个指令。屏幕弹出最近三十天的代码变更日志。季西输入自己的工号，筛选出三周前的提交记录。

变更记录显示：GC-2024-11-07，修改文件列表只有三个——SweepTrigger.java、HeapRegion.java、ReportHelper.java。没有涉及对象复制子程序的任何文件。

「看到了？」季西敲了敲屏幕。「我的变更里没有Copy模块。」

老堆凑近屏幕，把变更列表一行行看完。确实没有。

「那Copy模块是哪个提交改的？」

季西换了一个查询条件，搜所有涉及"copy"关键字的最近三十天变更。结果弹出来四条。他一条条点开：一条是钱境那边的JIT优化——涉及的是提前写入预取，不关GC的事；一条是白页的指令层面优化，改的是解释执行路径的参数；一条是仓库管理的老版本回退——

第四条，季西的手指悬在屏幕上没点下去。

提交人字段为空。

没有工号，没有签名，没有审批链。像一份无人认领的行李，安静地躺在变更记录里。变更时间是三周前的同一个晚上，和季西提交的时间只差十七分钟。修改的文件只有一个：ObjectCopy.java。

季西点开变更详情。

删掉了一行。

不是修改参数，不是替换逻辑——是删了年龄递增的那一行代码。整个ObjectCopy里的ageUpdate调用被抹掉了，从整个存活对象复制流程中彻底消失。删的那一行连注释都不留，整段代码看起来像是原本就没写过年龄这事儿。

老堆看完，背上一阵凉意。

「不是bug。是故意删的。」

季西没接话。他继续往下翻变更详情。删除操作的父级提交指向一个正常的版本。但这个变更本身没有经过任何review——没有提交消息，没有测试，什么都没有。

「谁有权限往ObjectCopy里写？」老堆问。

「不多。」季西把权限名单调出来。屏幕上列出六个人：季西自己、秦哨卡、贾淳、钱境、老堆——还有一个人，头像是灰色的，名字老堆没见过。

「白页？」

「他管字节码解释。」季西说。「他看得见所有指令和数据。」

两人对视了一眼。

季西看了一眼时间。从第三轮GC结束到现在，已经过去了一分半钟。第四轮GC的复制阶段已经开始——如果ObjectCopy已经被动过，那这一轮所有被复制的对象，年龄都会卡在零。

他不用看监控也知道问题有多大。

Survivor区里现在至少有几十个对象被复制过不止一次。没有一个晋升过。下一轮Minor GC时，Survivor会发现自己装不下了——不是因为对象多，而是因为该走的人没走。

担保机制会被触发。

担保机制不会区分「年轻但健康的好对象」和「年龄字段坏了的幸存者」。它会一次性把超出Survivor容量的所有对象全部推进老年代。那些本来应该再留几轮才能成熟的对象，会被直升到老年代。

然后它们中的大部分，在接下来的几秒内变成垃圾——坐在老年代里，等Full GC来处理。

而Full GC一次STW，时间是以秒计的。

「得把ObjectCopy修回来。」老堆说。

「在那之前——」季西已经拿起外套走向门口。

「在那之前，第四轮GC已经开了。」

监控终端上亮起一行新日志：

[GC-INFO] Minor GC #4 started. Eden: 438MB/512MB. Survivor: 58MB/64MB.

Survivor满了九成。

担保已经启动。老年代的大门正在打开。
