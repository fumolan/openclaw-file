# 第17章 空指针之夜

白页的办公室里堆满了字节码指令手册。每一条指令都对应着一个编号——从0到255，几乎每个数字都被占满了。

今天他追踪的一个问题，已经让应用崩溃了三次。

「每次都是在同一个位置——局部变量表里的引用居然是个null。」白页揉着眼睛把字节码文件摊在桌上。

展昭坐在对面，面前放着崩溃现场的栈帧快照。

「局部变量表里存的是引用地址。」展昭说，「对于这个方法而言，局部变量索引为1的位置应该存着一个ArrayList对象。但实际的快照显示——那里是null。」

「怎么可能？」白页皱眉，「在方法入口处，这个局部变量已经被赋值了——我看到入口处的字节码是把参数直接store到了局部变量索引1。参数不为null。」

「我重新检查一下字节码序列。」白页拿出放大镜。

他一行一行地看：

```
0: aload_0              // 加载this
1: invokespecial #1      // 调用父类构造
4: aload_1              // 加载第一个参数
5: putfield #2           // 存入this.field
8: aload_1              // 加载第一个参数（再次）
9: astore_1             // 存入局部变量1
10: aload_1             // 读取局部变量1——这里应该不为空
11: invokevirtual #3     // 调用size方法
14: ...
```

「看起来没问题。」白页说，「在第8-9行把参数值存到了局部变量1，第10行读取它。这中间没有任何赋值操作把null写入局部变量1。」

「但崩溃现场显示局部变量1是null。」

「那就只有一个解释——」白页翻身去找另一本手册，「有另一个线程修改了这块局部变量？」

「不可能。局部变量表是每个线程私有的栈帧数据。其他线程无法触碰。」

白页的手指停在了手册的一页上。

「那答案只有一个了——内存一致性问题。」他说，「看第9行的astore_1——把对象引用写入局部变量1。第10行读取它。但它们之间没有同步操作。」

「同一个线程内，按照程序顺序来看，第9行的写入应该对第10行可见啊。」

「理论上是可见的——as-if-serial语义保证同一个线程内的前后操作是有序的。但是——」白页指了指手册上的一行小字，「——局部变量表的读写操作会被编译器优化。」

「怎么优化？」

「编译器可能会给这个方法同时生成两个代码版本——第一个版本执行完整逻辑，第二个版本在某些条件下跳过某些步骤。如果线程在执行第二个版本时，被另一个线程修改了类的字段——」

「但局部变量不受其他线程影响。」

「局部变量不受其他线程影响，但编译器可能会做'冗余访问消除'。」白页说，「它看到aload_1之后跟着一个对同一个字段的访问——它觉得局部变量和字段的值是一样的，于是用局部变量替换了一遍字段访问。」

「但字段的值被另一个线程修改了——」

「对。按编译器优化后的版本，它用缓存在局部变量里的旧值去访问——而这个值实际上已经失效了。不，更准确地说——编译器可能在编译时就把一个字段的读替换成之前从局部变量里拿到的值。如果这个字段被另一个线程修改了，编译后的代码还是用旧值。」

「那会导致——

「会导致字节码层面的astore/aload看起来没写null，但实际上优化后的代码在用其他变量。」

展昭深吸一口气：「所以问题不在字节码本身——而在于编译器优化后的代码版本中，局部变量被优化掉了。」

「对。字节码文件里局部变量1明明存着对象引用——但编译器优化后，那段代码实际执行的机器指令根本不去读局部变量1，而是用之前缓存在寄存器里的值。」

「然而寄存器里的值由于某种原因变成了null？」

「是字段——它从字段里读取的值变成了null。」白页说，「为什么字段变成了null？因为另一条线程把它设为null了。而编译器优化后的代码没有重新读取字段——它用了之前的一个缓存值。」

「所以本质上是一个没加锁的字段访问——线程A写null，线程B用缓存读，读到的是null。」

「完全正确。」白页合上手冊，「这不是字节码的问题。这是并发访问共享字段却没有同步的问题。我们的字节码是正确的——但硬件和编译器在我们面前设置了一个迷宫。」

展昭陷入了沉思：「那我们的局部变量检查要在字节码层面还是编译层面做？」

「两个层面都要。」白页说，「字节码层面检查的是格式合法性和类型安全。编译层面检查的是——内存一致性和读取的安全性——这涉及到编译器优化过程中对字段访问的重排序。」

「那怎么确保下一次不出这个问题？」

「我们可以给编译器加一个检查——在每次从局部变量表读取引用时，如果它被用于invokevirtual调用，检查该值是否为null——如果为null，就在崩溃前记录完整的栈帧信息。」

「但这样会降低每次调用的性能。」

「比起诡异的空指针崩溃来说——这点性能损失是值得的。」白页说。

远处，一个应用线程又崩溃了。警报灯在走廊尽头闪烁。

「快。」展昭站起身，「第四个崩溃了。」

白页抓起手册和快照，跟着跑了出去。

白页和展昭赶到第四个崩溃现场时，看到的是一个已经被冻结的线程。监控终端上显示着线程的当前栈帧信息——最内层的方法调用停在了一次invokevirtual指令上——目标方法的对象引用为null。

「就是这个——」白页打开他的字节码手册，翻到invokevirtual那一页，「invokevirtual在执行之前会检查操作数栈顶的引用是否为null——如果是——抛出NullPointerException。」

「但问题是我们不知道为什么它是null。」展昭说。

白页没有直接回答，而是拿起了崩溃线程的完整栈帧日志看了起来。在栈帧中，他看到了一长串的方法调用链——每一个栈帧都对应着一次未完成的方法调用。

「看这个深度——」白页说，「调用栈一共24层。最顶层的栈帧是第0帧——一个接近尾声的方法。然后一路往下——第23帧是第一个调用的入口。」

「每个栈帧都保存着局部变量表和操作数栈。」展昭说。

「对。而我们需要确认的是——第11帧中的局部变量1——也就是我们之前检查的那个——是否真的在字节码层面被赋值了。」

白页把第11帧的字节码序列重新拆开，一行一行地检查。在字节码指令索引为134的位置，有一条astore指令——把操作数栈顶的引用存入局部变量1。

「赋值确实存在——指令134是astore_1。赋值源来自操作数栈——操作数栈顶的值来自指令131的aload_0——加载了this。但——」白页停了一下，「——this是什么？在这个方法中，this是HomeController的实例。HomeController的字段里有一个ReportService实例——而ReportService实例可能持有那个我们怀疑被设为null的对象。」

展昭走到白页的工作站前：「你的意思是——问题的根源不在局部变量1本身——而在局部变量1所引用的——对象的内部状态？」

「对。局部变量1里存的是ReportService实例的内存地址——这个地址本身是有效的——但ReportService实例内部的一个字段——已经被另一个线程设成了null。当我们通过这个地址去访问那个字段——得到一个null引用——然后把这个null引用作为方法调用的接收者——」

「空指针。」

「空指针。」

「但崩溃信息里写的是——局部变量1为null——而不是局部变量1的某个字段为null。」

「那就是报告系统的问题——」白页说，「——它只报告了直接的原因——'引用的对象的字段为null'——但报告工具把它简化为'引用为null'——因为它看到引用的解析结果是一个null。」

两人沉默了一会。展昭想到了一个解决方案：「我们可以在空指针发生时——打印完整的栈帧和对象引用链——不仅仅是'第几个局部变量是null'——而是从引用到字段的完整路径。」

「那需要更复杂的监控工具——捕获NPE的时候把所有相关的对象关系记录下来。」

「对。但这对调试来说至关重要——尤其是在多线程环境下——看到一个null——你不知道它是在哪里被设为null的。」

白页拿起电话：「季西——你在GC那边能看到对象的引用关系图吗？」

「能。我们用OOPMap记录对象的引用关系。」

「那好。当NPE发生时——帮我从GC的角度追踪一下——哪些地方指向了那个被设为null的字段。」

季西几分钟后回话：「追踪到了——那个字段在另一个线程的栈帧中被赋值为null。在一个缓存清理方法中——线程把某个过期的ReportService实例缓存清除——把字段设为了null——但它不知道另一个线程正在使用这个对象。」

「找到了——」白页放下电话，「是缓存清理线程在错误的时机清除了正在使用的对象。」

「那我们可以在缓存框架里加一个引用计数——当对象正在被使用时——不允许清理。」

「或者——在清理时检查对象是否在栈帧中被引用——如果发现栈帧引用——推迟清理。」

展昭在报告上写下了解析思路，然后合上本子：「今晚算是有了一个答案。至少下一次，当空指针出现的时候——我们知道从哪里开始挖了。」

白页望向窗外，天已经蒙蒙亮了。
