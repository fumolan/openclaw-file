# 第二十七章 搭积木

---

吉承是模式之城里最擅长"组装"东西的人。他的特长不是从零开始创建，而是把已有的组件拼在一起，组成更大的、更复杂的东西。

最近他接到了一个任务：设计一个文件系统过滤器。这个过滤器需要根据各种条件对文件进行过滤——按文件名过滤、按文件大小过滤、按创建时间过滤、按修改时间过滤、按文件类型过滤。而且这些条件可以任意组合：既要满足文件名条件，又要满足文件大小条件；或者满足文件名条件，或者满足文件大小条件；满足文件名条件但不满足文件大小条件……

"如果用继承来设计，"吉承在白板上画了一张图，"我们先有一个文件过滤器抽象类，然后派生出文件名过滤器、文件大小过滤器、创建时间过滤器、修改时间过滤器、文件类型过滤器。然后我们需要满足多个条件的过滤器，比如文件名且文件大小过滤器、文件名或文件大小过滤器……条件越多，组合越多，子类数量呈指数增长。"

"更糟糕的是，"吉承继续说，"如果以后要新增一种过滤条件，比如按文件权限过滤，那就要新增一大批子类——文件名且文件权限过滤器、文件大小且文件权限过滤器……之前的所有组合都要加一遍新条件。继承体系会变得庞大到无法维护。"

关察来看他的设计，摇了摇头："继承不适合这种场景。你应该用组合。"

"组合？"

"对。组合就是把多个对象组合成一个更大的对象，而不是通过继承来扩展。"关察在白板上画了另一张图，"你想搭积木，不是建族谱。继承是纵向的，子类继承父类，一环扣一环。组合是横向的，对象和对象组合在一起，一块积木搭在另一块积木上。"

关察的建议是这样的：定义一个文件过滤器接口，接口有一个方法叫accept，接收一个文件对象，返回是否接受这个文件。然后为每种过滤条件实现一个具体的过滤器类：文件名过滤器、文件大小过滤器、创建时间过滤器……每个过滤器类实现accept方法，判断文件是否满足条件。

关键在于：这些过滤器可以通过组合形成更复杂的过滤器。定义一个与过滤器，它持有两个文件过滤器，accept方法对两个过滤器都返回true时才返回true。定义一个或过滤器，它持有两个文件过滤器，accept方法对任一过滤器返回true时就返回true。定义一个非过滤器，它持有一个文件过滤器，accept方法对过滤器返回true时返回false，返回false时返回true。

"这样一来，"关察说，"你不需要为每一种组合定义一个子类。你只需要把已有的过滤器像积木一样组合起来。文件名过滤器与文件大小过滤器组合成一个新过滤器，这个新过滤器过滤出既满足文件名条件又满足文件大小条件的文件。文件名过滤器或文件大小过滤器组合成另一个新过滤器，这个新过滤器过滤出满足任一条件的文件。"

吉承开始实现这个设计。他定义了文件过滤器接口，实现了五种基础过滤器，又实现了三种组合过滤器——与过滤器、或过滤器、非过滤器。现在，任何复杂的过滤条件都可以用这五种基础过滤器和三种组合器组合出来。

比如要过滤出文件名以'.txt'结尾且文件大小大于1MB的文件：

```
文件过滤器 filter = new 与过滤器(
    new 文件名过滤器("*.txt"),
    new 文件大小过滤器(大于, 1024*1024)
);
```

要过滤出文件名以'.log'结尾或创建时间在七天前的文件：

```
文件过滤器 filter = new 或过滤器(
    new 文件名过滤器("*.log"),
    new 创建时间过滤器(早于, 七天前)
);
```

要过滤出文件名以'.tmp'结尾但不包括文件大小为0的文件：

```
文件过滤器 filter = new 与过滤器(
    new 文件名过滤器("*.tmp"),
    new 非过滤器(new 文件大小过滤器(等于, 0))
);
```

过滤器可以无限嵌套，组合出任意复杂的条件。新增一种过滤条件，只需要实现一个新的基础过滤器类，不需要修改任何已有的代码，也不需要新增任何组合过滤器类——组合的能力已经在与、或、非三种组合器里实现了。

"这就是组合模式的力量，"吉承在项目总结会上说，"单个过滤器和组合过滤器实现了同一个接口，可以被统一地对待。你可以把一个基础过滤器当作参数传给组合器，也可以把一个组合后的过滤器当作参数传给另一个组合器。组合后的过滤器本身也是一个过滤器，可以继续组合。这就是递归组合——组合的结果可以被再次组合。"

"组合和继承的区别是什么？"有人问。

"继承是'是一个'关系，"吉承说，"子类是一个父类。组合是'有一个'关系，一个对象包含另一个对象。继承是静态的，在编译时就确定了；组合是动态的，在运行时可以改变。继承是纵向扩展，一代一代往下传；组合是横向扩展，一块一块往上搭。"

"什么时候用继承，什么时候用组合？"

"当你想要复用实现，而且子类确实是父类的一种，行为也兼容，用继承。"吉承说，"当你想要灵活地组合功能，而且组合的方式在运行时可能变化，用组合。继承适合稳定的、层次分明的结构；组合适合动态的、自由组合的结构。你的文件过滤器场景，过滤条件经常变化，组合方式也经常变化，用组合正合适。"

文件系统过滤器后来成了吉承组合模式的代表作。他说过一句被经常引用的话："搭积木比建族谱有趣，积木怎么搭都可以，族谱建错了就全乱套了。继承像是在建族谱，一旦建立就很难改变；组合像是在搭积木，随时可以拆开重新搭。"

关察后来在模式之城的开发者论坛上写了一篇关于组合和继承区分的文章。文章里说了一个著名的比喻："继承是父子关系，组合是朋友关系。父子关系是天然的、不可选择的——你无法选择你的父亲。朋友关系是自主的、可选择的——你可以选择你的朋友。在选择代码结构的时候，尽量用组合代替继承，因为组合给你更多的选择自由。父子关系只有一条路走到底，朋友关系可以灵活组合。"

吉承看完文章之后回复了一句："继承是用来表达'是'的关系，组合是用来表达'有'的关系。正方形是矩形——可以用继承。文件过滤器有不同的过滤条件——用组合。不要把'是'和'有'搞混了。"

文件系统过滤器的成功让吉承开始在更多场景推广组合。后来模式之城的界面系统也用上了组合模式——窗口里有面板，面板里有按钮，按钮里有图标。每个组件都可以是单个的，也可以是组合的。窗口是组合，面板是组合，按钮也是单个组件。统一的结构让渲染、事件分发、布局计算都变得简单。吉承说："当你发现你的代码里有很多'类型'，而这些'类型'之间是层级关系而不是并列关系时，你就该考虑组合模式了。层级关系用组合表达，比用继承表达优雅得多。"

组合模式在模式之城的推广，让很多曾经被继承支配的恐惧得到了缓解。工程师们开始更多地考虑"我想要什么功能"而不是"我想要继承谁"。这种思维方式的转变，比任何模式本身都更有价值。

---

**本章涉及的设计模式：组合模式（Composite Pattern）**
- 将对象组合成树形结构以表示"部分-整体"的层次结构，使客户可以统一对待单个对象和组合对象
- 核心价值：通过递归组合，用少量基础组件构建复杂结构
- 与继承的区别：继承是"是一个"关系，静态、纵向扩展；组合是"有一个"关系，动态、横向扩展
- 适用场景：需要灵活组合功能、组合方式运行时可能变化的场景
