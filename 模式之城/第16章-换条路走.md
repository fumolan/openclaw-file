# 第十六章 换条路走

---

模板方法让策洛略在模式之城声名鹊起。政务中心的流程数字化项目大获成功之后，越来越多的部门找上门来请他帮忙设计流程。但很快，他就遇到了新的挑战。

这天，他的事务所来了一个重要的客户——模式之城的物流调度中心。调度中心负责整个城市的货物配送调度，每天要处理数万条配送任务。他们遇到了一个棘手的问题：同样的配送任务，在不同的时间段要使用完全不同的调度算法。

早高峰时段，城市拥堵严重，红绿灯多、小道堵、大路慢，配送车辆寸步难行。这个时候需要按"最短时间"算法来调度——宁愿绕路走远，也要避开拥堵路段。

午后平峰时段，路上车少人稀，但这个时候配送量也少了。如果还按"最短路程"跑，空驶率会很高。所以需要按"最低成本"算法来调度——争取每趟车的油钱和人工成本都降到最低。

夜间配送时段，交通最顺畅，但有的路段夜间限行，有的小区夜间不让进车。而且夜间配送的单量波动大——有时候一晚上几百单，有时候一晚上几十单。所以需要按"最多单量"算法来调度——在有限的车辆资源下，争取覆盖更多的订单。

更麻烦的是，调度算法的需求是不稳定的——"最短时间"算法用了两周，运营总监觉得不够智能，要求换成"预测拥堵"算法，能够基于历史数据预判接下来的拥堵情况；"最低成本"算法用了三天，财务总监觉得还不够省钱，要求换成"混合成本"算法——综合考虑油耗、保养、人工和折旧。

"代码改得我们快崩溃了！"调度中心的负责人诉苦道，"每次换算法，都要改一大段代码——改计算逻辑、改参数配置、改数据预处理。而且每改一次都得重新测试一遍，因为改的不是一个局部函数，是整个算法都被替换了。"

他越说越激动："最怕的是——改完了新算法，老算法还得留着，因为下个季度可能又要换回去。运营总监上个月说要'预测拥堵'，下周可能觉得不准，又换回'最短时间'。来回折腾，越来越乱。"

## 策洛略的第一反应

策洛略的第一反应是用模板方法来解决——把调度流程做成一个模板，不同的算法塞到不同的步骤里。但他刚画完骨架就发现不对。

模板方法解决的是"骨架不变、细节可变"的场景——步骤的数量和顺序是确定的，只是每个步骤内部的具体操作不同。但调度算法的问题不是某一个步骤在变，是**整个计算逻辑**在变。

"最短时间"算法先取物流数据，再查实时路况，再计算每条路线的时间，最后选最短路径。"预测拥堵"算法先取历史数据，再建模预测，再跑仿真，最后选最优路径。这两个算法的数据结构不同、中间结果不同、评判标准也不同——你没法把它们当成同一个骨架下的不同步骤。

"这已经把骨架本身都换掉了。"策洛略自言自语，"模板方法解决不了。需要另一种思路。"

他把这个问题带到了巩昌的铸造厂——巩昌是工厂模式的高手，两人经常一起探讨设计思路。

## 两个老朋友的对话

"你需要的不是模板方法。"巩昌听完之后说，"你需要的是一种'可以随时替换算法'的机制。"

"怎么说？"

巩昌在一张纸上画了两个方框，中间画了一个箭头。

"你看，你的调度系统是一个整体。它知道什么时候要调度、调度什么、调度给谁——这些东西是固定的，不管用什么算法都是一样。但它用什么样的方式去调度——这个是可变的，不同的算法有不同的逻辑。"

"所以你建议——"

"把可变的部分抽出来。"巩昌说，"抽成一个独立的接口。调度系统只认这个接口，不关心接口背后具体是什么算法。不同的算法只是这个接口的不同实现。你想换算法？换一个实现类就行了——调度系统本身不用改一行代码。"

策洛略盯着纸上的两个方框和中间的箭头，豁然开朗。

这不是模板方法。这是策略模式。

## 策略模式

策略模式的核心思想是：定义一系列的算法，把它们一个个封装起来，并且使它们可以相互替换。策略模式让算法的变化独立于使用它的客户。

策洛略回到事务所，开始重新设计调度系统。

他先定义了一个"调度策略"接口：

```
class 调度策略:
    def 计算路线(self, 订单列表):
        # 输入：订单列表
        # 输出：配送路线方案
        pass
```

这个接口很简单——你给我订单列表，我给你配送路线方案。至于你是怎么计算的、用了什么数据源、跑了多少迭代——接口不关心。只要输入和输出符合约定就行。

然后，他为每一种调度算法实现了这个接口：

```
class 最短时间策略(调度策略):
    def 计算路线(self, 订单列表):
        # 查询实时路况
        # 计算每条路线的时间
        # 选最短时间的路线
        return 路线方案

class 最低成本策略(调度策略):
    def 计算路线(self, 订单列表):
        # 计算每条路线的油耗
        # 计算每条路线的人工成本
        # 选总成本最低的路线
        return 路线方案

class 最多单量策略(调度策略):
    def 计算路线(self, 订单列表):
        # 分析订单分布
        # 基于车辆容量约束打包
        # 选覆盖率最高的路线
        return 路线方案
```

现在，调度系统——我们叫它"调度器"——不再关心算法细节。它只持有对一个"调度策略"的引用。在需要调度的时候，它调用策略的"计算路线"方法就行了：

```
class 调度器:
    def __init__(self, 策略):
        self.策略 = 策略

    def 开始调度(self, 订单列表):
        return self.策略.计算路线(订单列表)
```

想要哪个算法，就把哪个策略对象传给调度器：

```
调度器 = 调度器(最短时间策略())
调度器.开始调度(今日订单)
```

换算法？换个策略就行：

```
调度器 = 调度器(预测拥堵策略())
调度器.开始调度(今日订单)
```

不需要改调度器，不需要改调用方式。——三行代码的变动，就完成了整个算法的切换。

## 运行时切换

调度中心提出一个更高的要求：能不能在系统运行的过程中动态切换算法？比如每天早上八点自动切到"最短时间"模式应对早高峰，下午两点自动切到"最低成本"模式应对平峰，晚上八点自动切到"最多单量"模式应对夜间配送？

策洛略想了一下，引入了一个"策略选择器"。选择器根据当前的时间、实时的交通状况、订单的紧急程度等外部因素，自动选择合适的策略，动态地注入到调度器中。这样，一天中的不同时段，调度系统自动使用不同的策略，不需要人工干预。

但这里又出现了一个新问题：策略切换的时机。如果调度器正在执行一轮调度——正在读取订单数据、正在计算路线——此时策略被切换了，那么已经计算到一半的路线该怎么处理？继续用旧策略算完？还是放弃已算的部分用新策略重新算？

策洛略的方案是引入"切换窗口"。策略的切换不会立即生效，而是等到当前这一轮调度任务执行完成之后、下一轮调度任务开始之前，再切换策略。这样既保证了调度不中断，又实现了算法的无缝衔接。

## 自由的代价

模块建好了，策洛略在自己的测试环境里跑了一整套对比测试。

"最短时间策略"在早高峰的表现——配送时间平均缩短了23%，司机不用在路上干等红灯了。但燃油成本上升了15%——因为绕路走远了，油钱自然就多了。

"最低成本策略"在平峰的表现——成本下降了18%，车队的整体开支显著减少。但配送时间延长了7%，有客户投诉说"怎么送得越来越慢了"。

"最多单量策略"在夜晚的表现——单量提升了30%，更多的包裹在夜间被送了出去。但司机的工作时长增加了，有的司机凌晨还在送货，开始抱怨了。

"没有完美的算法。"策洛略看着测试数据叹了口气，"每种算法都有它的优点和代价。问题不是在找'最好的算法'——世界上不存在这种东西。问题是在找'当前条件下最合适的算法'。"

调度中心也意识到了这一点。他们不再追求唯一的"完美算法"，而是追求"在正确的时机使用正确的算法"。策略模式给了他们随时切换的自由，他们开始利用这个自由进行精细化的运营调优——早上用最短时间算法赶时效，下午用最低成本算法省油钱，晚上用最多单量算法提效率。

"这就对了。"策洛略对调度中心的人说，"策略模式的意义不在于让你找到'最好'的算法——因为不存在'最好'的算法。它的意义在于，让你随时可以换一种算法。世界在变，你的算法也应该能变。你不需要预测未来，你只需要准备好应对变化。"

## 后记

调度中心的运营效率提升了35%，客户满意度提升了20%，司机的投诉率下降了60%。

更让策洛略欣慰的是，调度中心的开发团队不再为算法变更而痛苦。每次有新的算法需求——比如又有一种新的优化思路——他们只需要写一个新的策略类，实现调度策略接口，然后在策略选择器中注册一下就行了。现有的一行代码都不用改。

"模板方法固定了骨架，策略模式固定了接口。"策洛略在他的笔记中写道，"骨架告诉你先做什么后做什么；接口告诉你做什么但不规定怎么做。前者的灵活度在于'细节可以不同'，后者的灵活度在于'整体可以替换'——理解这个区别，就能在正确的场景中选择正确的工具。"

他合上笔记本，又想起巩昌的提醒：策略模式虽然灵活，但如果策略越来越多——十个、二十个、五十个——管理和维护的成本也会急剧上升。他拿起笔，在笔记的末尾补充了一句：

"自由是好的，但要有边界。策略太多了，也是一种负担。不要为了灵活而灵活——需要一种算法的时候，别写十种策略，等着需求来。在接口上做可扩展设计，在实例上不过度设计。"

---

**本章涉及的设计模式：策略模式（Strategy Pattern）**
- 定义一系列算法，把它们一个个封装起来，并且使它们可以相互替换
- 核心价值：算法的变化独立于使用它的客户，实现运行时算法切换
- 与模板方法的区别：模板方法改变算法内部的"步骤"；策略方法改变算法的"整体"
- 适用场景：同一行为有多种实现方式，且需要在运行时动态切换
- 最佳实践：搭配策略选择器，实现策略的自动/动态切换
