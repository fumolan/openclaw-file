# 第十五章 固定的骨架

---

在模式之城的东南角，有一座不起眼的小楼，门上挂着一块木牌："策洛略事务所——流程设计专家。"

策洛略是这座城市里最擅长"规定动作"的人。他设计的流程、制定的规范，让每一件事都有章可循——从企业注册到项目审批，从补贴申请到资质认证，每一件事都被他梳理成了清晰的执行步骤。

但是有一天，他发现了一个让他头疼的问题。

## 相同的步骤，不同的细节

模式之城的政务中心找到策洛略，请他帮忙优化三个流程的数字化：企业注册、项目审批和补贴申请。

策洛略拿到需求文档一看，发现这三个流程都遵循几乎相同的步骤：

第一步是**资料提交**——申请人把材料交上来。第二步是**初审**——工作人员核对材料是否齐全。第三步是**复核**——上级审核材料的真实性和合规性。第四步是**审批**——做出最终决定。第五步是**结果通知**——把结果告知申请人。

骨架一样，但每一步的具体内容完全不同。

企业注册的"初审"环节需要核对企业名称是否重复、注册资本是否达标、经营范围是否合规——每个检查项背后有不同的数据源和验证规则。项目审批的"初审"环节需要核对项目预算是否在额度内、可研报告是否完备、环评文件是否过期——涉及三个不同的审批系统。补贴申请的"初审"环节需要核对申请人资格是否有效、补贴上限是否超额、证明材料是否真实——背后关联着资格数据库和补贴规则引擎。

如果为每个流程写一套完整的代码，五分之四的代码都是重复的——"资料提交→初审→复核→审批→通知"这套流程框架，三个系统各写一遍。只有十分之一的逻辑是真正不同的——具体的审核内容和数据验证规则。

这不只是浪费，更是维护噩梦。当流程骨架发生变化时——比如政策规定新增了"公示"环节——三个系统的骨架都要改，很容易改漏一个。而且，三个系统的骨架代码可能渐渐变得不一致——有的做了性能优化，有的没有——导致同样的流程在不同的系统中跑出不同的结果。

## 策洛略的思考

策洛略把三个流程的骨架抽了出来，仔细对比，然后画了一张对比图：

```
        企业注册        项目审批        补贴申请
        ────────        ────────        ────────
步骤1： 资料提交         资料提交         资料提交
步骤2： 名称核查/       预算核查/       资格核查/
        资本核查/       报告核查/       上限核查/
        范围核查        环评核查        材料核查
步骤3： 真实性复核       技术性复核      资格复核
步骤4： 审批决定         审批决定         审批决定
步骤5： 结果通知         结果通知         结果通知
```

对比图清楚地显示——骨架完全一样（步骤1、3、4、5），只有步骤2的具体内容不同。

"如果能固定骨架，只允许在固定的位置上填入不同的内容就好了。"策洛略喃喃自语。

他想到了——模板方法模式。

模板方法模式的核心思想是：在一个方法中定义一个算法的骨架，而将一些步骤延迟到子类中实现。模板方法使得子类可以在不改变算法结构的情况下，重新定义算法中的某些特定步骤。

通俗地说：先画好一张通用菜谱，把"备料→切菜→烹饪→装盘"这些大步骤定死。但"备什么料""切多细""用什么火候""怎么摆盘"这些细节留给各个菜系的师傅自己去发挥。鲁菜师傅做"糖醋鲤鱼"，川菜师傅做"水煮鱼"，虽然都是鱼，但用的料、切的刀法、火候和配料完全不同——然而"备料→切菜→烹饪→装盘"这个大框架是不变的。

## 实践

策洛略开始动手。

他先定义了一个抽象的"审批流程模板"类。这个类规定了五个步骤的结构，以及一个执行流程的方法——执行方法会按顺序调用这个五个步骤。骨架写在这儿，一步都不许少，一步都不许乱：

```
class 审批流程模板:
    资料提交()      # 具体逻辑由子类实现
    初审()          # 具体逻辑由子类实现
    复核()          # 具体逻辑由子类实现
    审批()          # 具体逻辑由子类实现
    结果通知()      # 具体逻辑由子类实现

    def 执行():
        资料提交()
        初审()
        复核()
        审批()
        结果通知()
        # 完成！骨架不变，血肉可变。
```

然后，他为每个具体的审批流程创建了一个子类，重写父类模板中的步骤方法：

```
class 企业注册流程(审批流程模板):
    初审():
        检查企业名称是否重复()
        检查注册资本是否达标()
        检查经营范围是否合规()

class 项目审批流程(审批流程模板):
    初审():
        核对项目预算()
        核查可研报告()
        审核环评文件()

class 补贴申请流程(审批流程模板):
    初审():
        审核申请人资格()
        核验补贴上限()
        检查证明材料()
```

现在，当系统需要执行一个审批时，只需要创建一个对应的流程实例，调用"执行"方法即可。"执行"方法定义在父类模板中——它规定了流程的骨架。每个步骤的具体实现定义在子类中——它提供了流程的血肉。父类做骨架，子类填血肉。两者各司其职，互不干扰。

策洛略给这个设计取了个名字："骨架填充法。"

## 钩子

没过多久，新的需求来了。

政务中心要求在企业注册流程完成后，额外发送一条短信通知申请人。但其他流程不需要这个功能——项目审批用邮件通知，补贴申请用站内信通知，各有各的通知方式。

策洛略不想在企业注册流程中硬编码短信发送逻辑，因为那样会破坏模板的通用性——你给企业注册加了短信发送，那下次项目审批要加邮件通知时，是不是也得往模板里加？这样模板会越来越臃肿，越来越不通用。

他想到了一个机制：**钩子方法**。

钩子方法是在模板流程中预定义的、默认不做任何事情的方法。子类可以根据需要选择性重写它，不需要的时候忽略它。钩子的存在不影响骨架的完整性——它就像是骨架上的一个挂钩，想挂东西就挂上，不想挂就空着。

策洛略在模板中加了一个"结束钩子"：

```
class 审批流程模板:
    ...
    结束钩子():
        # 默认什么都不做，留给子类选择性实现
        pass

    def 执行():
        资料提交()
        初审()
        复核()
        审批()
        结果通知()
        结束钩子()  # 五个标准步骤结束后，执行钩子
```

然后，在企业注册流程中重写结束钩子：

```
class 企业注册流程(审批流程模板):
    ...
    结束钩子():
        发送短信通知(申请人)
```

现在，企业注册流程在执行完标准五步后，会自动调用结束钩子，发送短信通知。而项目审批和补贴申请流程不受影响——它们的结束钩子啥也不做。

钩子机制让模板既保持了通用的骨架，又提供了按需扩展的弹性。

## 不变的骨架与多变的血肉

策洛略的设计让政务中心非常满意。后来，他们又为这个系统增加了十几个新的审批流程——建筑许可、经营备案、税收优惠、环保认证、食品安全许可……每一个新流程只需要做一件事：创建一个子类，实现那几个差异化步骤。然后框架会自动完成剩下的工作。

"模板方法的精髓在于，"策洛略后来在技术分享会上说，"把不变的部分和变化的部分分开。不变的骨架，你写一次，写清楚、写严谨。变化的血肉，你每次填不同的——每个场景填自己的内容。骨架定好了，不管血肉怎么变，骨架子不散，系统就不会乱。"

"那如果骨架本身要变呢？"有人举手提问。

"那是另一个问题。"策洛略笑了笑，"模板方法假设骨架是相对稳定的。如果骨架频繁变化，那说明你选择的抽象层级不对——你把不该固定的东西固定了。或者说，你的系统本身还没稳定下来，不应该用模板方法强行定型。"

他顿了顿，补充道："不过，就算骨架偶尔要变，也比没有骨架强。没有骨架的代码就像一堆散落的零件——想拼都拼不起来。有骨架至少有个框架，至少有个方向。"

## 尾声

策洛略的事务所后来成了模式之城的流程设计标准制定者——他的"模板方法"理念被广泛应用在各类系统设计中。

但策洛略自己知道，模板方法只是工具，不是宗教。骨架太死板会限制灵活性，骨架太灵活又失去了模板的意义。真正的好设计，是在稳定和灵活之间找到一个合适的平衡点——而这个平衡点，每个系统都不一样，需要根据实际场景去摸索。

他正在琢磨的下一件事，就是如何让骨架更灵活一些——在维持骨架稳定性的同时，给变化留下更多的空间。

---

**本章涉及的设计模式：模板方法模式（Template Method Pattern）**
- 定义一个操作中的算法骨架，将一些步骤延迟到子类中实现
- 核心价值：复用算法结构，消除重复代码，统一流程框架
- 关键机制：钩子方法（Hook）——在骨架中预留的可选扩展点
- 适用场景：多个场景有相同的执行骨架但具体实现细节不同
- 注意事项：骨架应该相对稳定，频繁变化的场景不适合模板方法
